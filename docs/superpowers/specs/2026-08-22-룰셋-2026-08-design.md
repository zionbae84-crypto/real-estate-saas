# 룰셋 2026-08 반영 설계

**작성일:** 2026-08-22
**상태:** 승인됨
**선행:** Plan A(재무 엔진), 룰셋 검증 — 둘 다 main

## 1. 왜 하는가

`rules/2026-03.json`의 값 넷이 현행 고시와 어긋나고, **전부 사용자에게 "실제보다 더 살 수 있다"고 말하는 방향**이다. 이 제품의 방침은 "사지 말아야 할 때를 말해주는 것"이므로 이 방향의 오차는 출시를 막는 사유다.

엔진으로 측정한 실제 영향:

| 프로필 | 현재 룰셋 | 현행 고시 | 차이 |
|---|---|---|---|
| 연봉 6천 / 현금 2억 / 생애최초 / 규제지역 | 5.35억 | 4.77억 | −5,800만원 |
| 연봉 8천 / 현금 2.5억 / 생애최초 / 비규제 | 6.93억 | 6.19억 | −7,400만원 |
| 연봉 1억 / 현금 3억 / 규제지역 | 4.83억 | 4.83억 | 0 (LTV가 제약) |
| 연봉 1.5억 / 현금 5억 / 규제지역 | 7.89억 | 7.89억 | 0 (LTV가 제약) |

오차는 **DSR이 제약인 구매자**, 즉 소득 대비 무리하는 쪽에 가까운 사람에게만 난다. 정확히 우리가 보호하려는 대상이다.

## 2. 확인된 현행 고시값

| 항목 | 2026-03 | 2026-08 | 출처 |
|---|---|---|---|
| 스트레스 금리 하한 | 1.5% | **3.0%** | 10·15 대책 (수도권·규제지역 주담대) |
| 시중 주담대 금리 | 4.2% | **4.53%** | 한은 가중평균, 26-06 고정형 |
| 보금자리론 30년 | 4.2% | **5.20%** | 주금공 26-08-01 공시, u-보금자리론 |
| 디딤돌 | 3.2% | **3.55%** | 범위 2.45~3.55%의 상단 |
| 대출 절대한도 | 6억 단일 | **15억↓ 6억 / 15~25억 4억 / 25억↑ 2억** | 10·15 대책 |
| 규제지역 LTV | 40%, 생애최초 70% | 변경 없음 | 확인함 |

정책대출 금리는 둘 다 **범위의 위쪽**을 쓴다. 우대금리는 사람마다 달라 보장할 수 없고, 높은 금리는 한도를 낮춰 안전한 방향으로 틀린다.

시중금리는 전체 평균 4.36%가 아니라 **고정형 4.53%** 를 쓴다. 엔진이 만기 30년 원리금균등 고정 상환을 가정하므로 고정형이 대응되는 값이고, 더 보수적이다.

## 3. 범위

### 하는 것

- `absoluteCap`을 스칼라에서 주택가격 구간 배열로 스키마 변경
- `calcMaxLoan`이 가격에 따라 캡을 정하도록 수정
- `buildSearchSegments`가 캡 구간 경계에서도 탐색을 나누도록 수정
- `parseRules`의 정책대출 불변식을 구간 캡에 맞게 수정
- `rules/2026-08.json` 신규 생성
- `rules/2026-03.json`을 새 스키마로 마이그레이션 (값의 의미는 불변)
- UI가 읽는 룰셋을 `2026-08.json`으로 교체
- 골든 테스트 기대값 재계산

### 하지 않는 것 (별도 과제)

- **디딤돌 자격별 한도 축** — 일반 2.5억 / 생애최초 3억 / 신혼 4억. 지금은 2.5억 단일이라 **과소 계상(안전한 방향)** 이다. 이 축을 넣으려면 `policyLoans[].maxAmount`를 자격 조건별로 쪼개야 하고 정책대출 매칭·탐색 절벽 계산이 함께 복잡해진다. 출시를 막는 방향이 아니므로 미룬다.
- **취득세 구간의 포함/배타 경계** — §4.1 참조. 배타적 해석이 안전한 방향이라 이번에 건드리지 않는다.
- **수도권/비수도권 축** — 이 파일은 여전히 수도권 전용이다.

## 4. 설계

### 4.1 `absoluteCap` 스키마

```jsonc
"absoluteCap": {
  "_note": "10·15 대책. 수도권·규제지역 주담대 한도를 주택가격 구간별로 나눈다. upTo는 포함(이하)이다 — 이 파일의 다른 구간 배열(housingBond, brokerageFee)과 취득세는 배타적(미만)이라 다르므로 주의할 것. 규제 원문이 '15억 이하'라고 쓰기 때문이며, 배타적으로 읽으면 정확히 15억일 때 한도를 2억 과소 계상한다.",
  "brackets": [
    { "upTo": 1500000000, "amount": 600000000 },
    { "upTo": 2500000000, "amount": 400000000 },
    { "upTo": null,       "amount": 200000000 }
  ]
}
```

**조회는 `price <= upTo`(포함)로 한다.** 기존 구간 배열들은 전부 `price < upTo`(배타)인데 여기만 다르다.

이유: 규제 원문이 "15억 원 이하 → 6억"이다. 배타적으로 읽으면 가격이 정확히 15억일 때 다음 구간(4억)으로 떨어져 **2억을 과소 계상**한다. 방향은 안전하지만 15억은 실제로 나올 법한 호가이고 오차 규모가 크다.

취득세의 배타적 해석은 "세금을 더 걷는" 안전한 방향이라 이번에 바꾸지 않는다. 다만 두 의미가 한 파일 안에 공존하므로:

- 조회 함수 이름과 doc 주석에 포함/배타를 명시한다
- 룰셋 파일의 `_note`에도 남긴다
- `parseRules`의 구간 정렬 검증기(`upTo` 오름차순, 마지막만 null)는 **공유한다** — 검증 규칙은 동일하고, 다른 것은 조회 시점의 비교 연산자뿐이다

### 4.2 `calcMaxLoan`

```
CAP: Math.floor(rules.absoluteCap)
  →
CAP: Math.floor(calcAbsoluteCap(rules, price))
```

`calcMaxLoan`은 이미 `price`를 받으므로 시그니처는 바뀌지 않는다. `calcAbsoluteCap(rules, price)`는 `loan-limit.ts`에 둔다.

정책대출 경로는 지금처럼 캡을 걸지 않는다 (`calcPolicyLimit` 참조).

### 4.3 `parseRules` 불변식

현재: `모든 i에 대해 policyLoans[i].maxAmount <= absoluteCap`

이 불변식은 "정책대출 경로에 캡을 안 걸어도 안전하다"를 데이터 단에서 보장한다. 캡이 구간 함수가 되면 다음으로 바꾼다.

> 각 정책대출 상품의 `maxAmount`는, **그 상품이 자격을 유지하는 최고 주택가격에서의 캡** 이하여야 한다.

- `eligibility.maxHousePrice`가 있으면 그 가격에서의 캡과 비교한다. 보금자리론은 `maxHousePrice` 6억 → 6억 구간의 캡 6억과 비교 → 3.6억 ≤ 6억, 통과.
- `maxHousePrice`가 없으면 **가장 낮은 구간의 캡**(2억)과 비교한다. 가격 상한이 없는 상품은 어떤 가격에서도 자격이 있으므로 가장 낮은 캡이 걸릴 수 있다.

### 4.4 탐색 구간

`buildSearchSegments`가 현재 정책대출 절벽(`eligibility.maxHousePrice`)에서만 구간을 나눈다. 여기에 **캡 구간 경계**를 합집합으로 더한다.

탐색 상한이 100억(`SEARCH_UPPER_BOUND`)이라 15억·25억 경계가 탐색 범위 안에 있다. 나누지 않으면 이분 탐색이 절벽을 가로질러 진짜 최대를 지나칠 수 있다.

포함 경계이므로 경계값 자체는 하위 구간에 속한다 — 기존 정책대출 절벽 처리와 동일한 규칙이다.

### 4.5 파일과 배선

- `rules/2026-08.json` 신규. `version: "2026-08"`, `effectiveFrom: "2026-08-01"`
- `rules/2026-03.json`을 새 스키마로 마이그레이션:
  ```jsonc
  "absoluteCap": { "brackets": [{ "upTo": null, "amount": 600000000 }] }
  ```
  값의 의미는 100% 동일하다(모든 가격에서 6억). 파일이 계속 로드·테스트 가능하도록 유지하는 것이 목적이다.
- `src/state/useAffordability.ts`의 import를 `2026-08.json`으로 교체
- `2026-08.json`의 `_scope` 주석 갱신: 스트레스 3%와 구간별 캡이 **둘 다 수도권·규제지역 적용**이라 이 파일의 범위와 일치한다는 사실을 명시한다. 스칼라로 남은 `stressDSR.surcharge`가 왜 지금은 문제가 아닌지 읽는 사람이 알 수 있어야 한다.

## 5. 테스트

### 5.1 골든 테스트 재계산

`golden.test.ts`의 기대값이 대부분 바뀐다 — 스트레스 1.5%→3%가 DSR 제약 프로필 전부를 움직인다.

**기대값은 손으로 다시 계산해 검증한다. "테스트가 통과하도록 출력을 붙여넣는" 방식을 쓰지 않는다.** 골든 테스트의 목적은 회귀 감지인데, 출력을 그대로 기대값으로 삼으면 그 목적이 사라진다.

각 골든 케이스마다 어느 제약이 걸렸는지(`binding`)를 함께 단언해, 값이 맞는 이유까지 고정한다.

### 5.2 새로 필요한 테스트

- **캡 구간 경계**: 정확히 15억, 15억−1원, 15억+1원, 정확히 25억, 25억±1원에서 `calcAbsoluteCap`이 각각 6억/6억/4억/4억/2억을 내는지
- **탐색 정확성**: 15억·25억을 넘나드는 프로필에서 `calcAffordablePrice`가 진짜 최대를 찾는지 — 절벽 근처를 `PRICE_STEP` 단위로 훑는 브루트포스와 대조한다
- **불변식**: `maxAmount`가 해당 상품 자격 최고가의 캡을 넘는 룰셋이 `parseRules`에서 거부되는지
- **마이그레이션 동등성**: 새 스키마의 `2026-03.json`이 파싱되고, 그 룰셋으로 계산한 결과가 마이그레이션 전과 **동일한지**
- **UI 배선**: 화면이 `2026-08` 라벨을 표시하는지 (`formatRuleVersionLabel`은 이미 버전 비의존적으로 작성돼 있다)

## 6. 위험

**골든값 재계산이 이 작업의 가장 큰 위험이다.** 손 계산이 틀리면 틀린 값이 회귀 기준으로 굳는다. 완화책: 각 케이스의 `binding`을 함께 단언하고, 최소 한 케이스는 제약별로 독립 계산해 교차 검증한다.

**포함/배타 혼재도 위험이다.** 같은 파일 안에 두 의미가 공존하므로, 나중에 누가 `calcAbsoluteCap`을 다른 구간 조회 코드에 맞춰 "정리"할 수 있다. 완화책: 함수 doc과 룰셋 `_note` 양쪽에 이유를 남기고, 경계 테스트가 뒤집기를 잡도록 한다.

## 7. 완료 기준

- `rules/2026-08.json`이 §2의 값을 담고 파싱된다
- `rules/2026-03.json`이 새 스키마로 파싱되고 결과가 마이그레이션 전과 동일하다
- 15억·25억 경계에서 캡이 정확하다 (포함 경계)
- 절벽을 넘나드는 탐색이 브루트포스와 일치한다
- 골든 기대값이 손 계산으로 검증됐고 `binding`까지 고정됐다
- 화면이 `2026-08` 룰셋으로 계산한다
- 전체 스위트 통과, 타입체크 클린
