# 예산 기반 부동산 추천 서비스 — 설계 문서

- **작성일**: 2026-08-16
- **상태**: 승인됨 (구현 계획 수립 대기)
- **범위**: MVP 1개 제품 (예산 기반 추천). 부동산 종합 진단은 별도 제품으로 후속 진행

---

## 1. 한 줄 정의

수도권 실거주 주택 구매자(무주택·갈아타기)가 로그인 없이 보유 현금·소득·기존 부채를 입력하면,
2026년 대출 규제를 반영한 **실구매 가능 예산**을 산출하고,
그 예산 안의 아파트 단지/평형을 **재무 안전성 순**으로 보여주는 웹 서비스.

## 2. 왜 만드는가

### 시장의 빈 곳

기존 서비스는 전부 **"매물 → 대출 알아보기"** 순서다. 호갱노노는 지도 탐색, 바로이집은 조건 매칭,
뱅크몰은 대출 비교, 부동산계산기.com은 한도 계산 — 각각 존재하지만 **"내 돈 → 진짜 살 수 있는 가격대 → 그 안의 단지"**
역방향 흐름을 제공하는 서비스가 없다.

### 지금인 이유

2025년 7월 스트레스 DSR 3단계 시행과 수도권 주택구입 목적 주담대 6억원 캡으로,
일반 소비자가 자기 대출한도를 스스로 계산하는 것이 사실상 불가능해졌다.
12억 아파트에 LTV 70%를 적용하면 8.4억이 나와야 하지만 실제로는 6억에서 잘린다.
연소득 1억 기준 한도가 이전보다 1억 원 이상 감소했다.

### 차별점

1. **진입점이 매물이 아니라 돈이다** — 부대비용을 예산에서 먼저 차감한 실구매력을 제시
2. **재무 안전성으로 줄 세운다** — "오를 집"이 아니라 "무리하지 않는 집". 기존 앱이 하지 않는 영역
3. **"살 수 없다"고 말한다** — 결과 0개를 억지로 채우지 않는다
4. **재무정보를 서버로 보내지 않는다** — 마케팅 문구가 아니라 아키텍처 사실

## 3. 확정된 범위

| 항목 | 결정 |
|---|---|
| MVP 제품 | 예산 기반 추천 1개 (진단은 후속) |
| 타겟 사용자 | 무주택 실거주 구매자 + 1주택 갈아타기 |
| 추천 단위 | 단지/평형 단위 + 네이버부동산 외부 링크 |
| 랭킹 기준 | 재무 안전성(상환부담률) 오름차순 |
| 계정 | 없음. localStorage만 사용 |
| 지역 | 수도권 (서울·경기·인천) |
| 형태 | 웹, 모바일 반응형 |
| 아키텍처 | 빌드타임 ETL + 정적 데이터 서빙 |

### 범위 밖 (MVP에서 하지 않음)

- 개별 매물(호가) 데이터 — 네이버부동산 등은 크롤링 불가, 제휴 필요
- 전국 확대 — 데이터만 확장하면 되므로 후속
- 계정·구독·알림 — 재무정보 미저장 원칙과 충돌하지 않는 범위에서 후속 검토
- 다세대·단독주택 — 실거래 데이터 특성이 달라 별도 파이프라인 필요
- 양도세 자동 계산 — 변수가 과다. 직접 입력받고 미입력 시 경고
- 수익형 부동산(DSCR/RTI) — 진단 제품 영역

## 4. 아키텍처

```
[오프라인 / 배치]
  국토부 실거래가 API ──> 파이프라인 ──> 정적 JSON ──> CDN
                                                        │
[온라인 / 브라우저]                                      │
  사용자 입력 ──> 재무 엔진 ──> 랭킹 ──> 화면  <────────┘
       │
       └─ localStorage (서버로 전송되지 않음)
```

두 세계는 만나지 않는다. 파이프라인은 사용자를 모르고, 웹앱은 서버를 모른다.
사용자 재무정보가 네트워크를 타는 경로가 코드상 존재하지 않는다.

### 접근법 선택 근거

| 접근법 | 판단 |
|---|---|
| **A. 빌드타임 ETL + 정적 서빙** | **채택.** 재무정보 무전송이 보장되고, 운영비 0, 수도권 규모(약 1.5만 단지)에서 gzip 후 1MB 내외로 수용 가능 |
| B. 서버 DB + API | 미채택. 예산 계산 파라미터가 서버 로그에 남아 "저장 안 함" 약속이 흐려진다. 확장성은 지금 필요 없고 A→B 전환은 ETL 산출물 목적지만 바꾸면 된다 |
| C. 국토부 API 실시간 호출 | **불가.** API가 `지역코드 + 조회월` 단위로만 조회되어 전역 랭킹이 원리적으로 불가능 |

## 5. 데이터 파이프라인 (`scripts/pipeline/`)

각 단계는 이전 단계의 출력만 읽는다. 독립 실행·독립 테스트 가능.

| 단계 | 입력 | 하는 일 | 출력 |
|---|---|---|---|
| `fetch` | 법정동코드 목록 | 수도권 시군구 × 최근 12개월 실거래가 수집. 증분 캐시 | `raw/{지역코드}-{년월}.json` |
| `normalize` | `raw/` | 단지 식별키 생성, 표기 흔들림 정규화 | `normalized.json` |
| `aggregate` | `normalized.json` | 단지 × 전용면적 구간별 집계 | `complexes.json` |
| `emit` | 집계 결과 + 지역 메타 | 압축, 매니페스트 생성 | `data/` |

### 데이터 소스

- **국토부 아파트 매매 실거래가 상세 자료 API** (공공데이터포털) — 무료, 합법
- **행정안전부 법정동코드** — 수도권 시군구 코드 세트
- 규제지역 지정 현황 — 룰셋 파일에 수동 반영

### 단지 식별 (`normalize`) — 가장 어려운 부분

국토부 데이터는 같은 단지가 "○○아파트", "○○아파트1차", "○○1단지"로 흔들린다.

- 식별키: `법정동코드 + 건축년도 + 정규화된 단지명`
- 정규화: 공백/특수문자 제거, 차수·단지 표기 통일
- **완벽한 병합은 불가능하다고 전제한다.** 병합되지 않은 잔여 건수를 리포트로 출력하여
  사람이 확인할 수 있게 한다. 조용히 틀리는 것보다 낫다.

### 집계 (`aggregate`)

단지키 × 전용면적 구간별로:

- 최근 6개월 거래 **중위값** (대표 시세)
- 거래 건수
- 최고/최저 거래가
- 3개월 / 1년 변동률

**품질 플래그**: 최근 6개월 거래가 3건 미만인 평형은 제외하지 않고
`lowConfidence: true`로 표시한다. 중위값이 1~2건으로 흔들리는 것을 숨기면 신뢰가 무너진다.

### 산출물 (`data/`)

| 파일 | 내용 |
|---|---|
| `complexes.json` | 단지 × 평형별 시세, 신뢰도 플래그, 변동률 |
| `regions.json` | 시군구 메타, 규제지역 구분 |
| `manifest.json` | 데이터 버전, 생성 일시, 실거래 데이터 기준일, 적용 룰셋 버전 |

## 6. 재무 엔진 (`src/lib/finance/`)

전부 **순수 함수**. 부작용 없음. 브라우저·노드 양쪽에서 동작. 테스트의 90%가 여기에 집중된다.

### 핵심 함수

```
calcMaxLoan(profile, rules, price) -> LoanLimit
  max( min(LTV한도, DSR한도, 지역절대캡), 정책대출한도 )
  - LTV: 지역·주택가격·생애최초 여부에 따라 분기
  - DSR: (기존부채 연원리금 + 신규대출 연원리금) / 연소득 <= 한도
         신규대출 원리금은 스트레스 가산금리를 적용해 계산
  - 절대 캡: 수도권 주택구입 목적 6억
  - 정책대출: 은행 경로와 나란히 놓인 "선택지"이지 반드시 따라야 하는
    상한이 아니다. 최소값에 함께 넣으면 자격이 있다는 이유만으로 한도가
    줄어든다(무주택 구매자가 동일 조건 갈아타기 구매자보다 덜 빌리게 됨).
    자격 상품이 없으면 0으로 표현한다.
  정책대출 한도는 매매가에 의존(주택가격 상한)하므로 이 함수가 직접
  도출한다. 호출자가 따로 넘기지 않는다.
  반환값에 "어느 한도가 이 금액을 만들었는지"를 반드시 포함한다

calcAffordablePrice(profile, rules) -> number
  대출한도는 집값에 의존하고(LTV) 집값은 대출한도에 의존하는 순환 참조.
  이분 탐색으로 수렴시킨다.

calcAcquisitionCosts(price, profile) -> CostBreakdown
  취득세(가액구간 · 생애최초 감면) + 중개보수(상한요율) + 법무비 + 이사/기본 인테리어 추정

calcSafetyScore(profile, rules, loanAmount) -> SafetyScore
  월 상환액 / 월 세전 소득 = 상환부담률
  ※ 분모는 세전(gross) 소득이다. 한국의 DSR류 기준선이 관례적으로 세전
    대비로 고시되므로, safetyThreshold의 25% / 35% 임계값은 세전과 짝을
    이룰 때만 의미가 맞는다(가처분소득으로 바꾸면 같은 임계값이 훨씬
    엄격해져 등급 체계가 어긋난다).
  매매가는 인자가 아니다 — 부담률은 상환액과 소득만으로 결정된다
  기본 시나리오와 금리 +2%p 스트레스 시나리오를 모두 산출
  랭킹 키로 사용

matchPolicyLoans(profile, rules) -> PolicyLoan[]
  디딤돌 · 보금자리론 · 신생아특례 · 생애최초 자격 매칭
```

### 실구매력 정의

부대비용과 LTV가 모두 매매가에 의존하므로 단순 뺄셈으로 정의할 수 없다.
**아래 부등식을 만족하는 최대 매매가 P**가 실구매력이며, `calcAffordablePrice`가 이분 탐색으로 구한다.

```
(P - calcMaxLoan(profile, rules, P)) + calcAcquisitionCosts(P, profile) <= 가용현금
```

좌변 첫 항이 자기부담금(계약금+잔금 중 현금 부분), 둘째 항이 취득 부대비용이다.
화면에는 이 결과를 "대출한도 / 부대비용 / 실구매력" 세 값으로 분해해 보여준다.

**용어**: 이 문서에서 "가용현금"은 사용자가 주택 구매에 실제 투입 가능한 현금 총액을 뜻한다.
갈아타기의 경우 기존 주택 순자산이 여기에 합산된다.

### 갈아타기 처리

프로필에 `existingHome: { expectedSalePrice, remainingLoan }`이 추가되고,
`순자산 = 예상매도가 - 상환할대출 - 매도부대비용`이 가용현금으로 흘러 들어간다.

**양도세는 자동 계산하지 않는다.** 보유기간·거주기간·조정지역·일시적 2주택 등 변수가 과다하다.
직접 입력받고, 미입력 시 "양도세가 반영되지 않았습니다" 경고를 표시한다.
추정해서 틀리느니 모른다고 하는 편이 낫다.

## 7. 규제 룰셋 (`rules/`)

**코드는 룰셋을 읽기만 한다.** 규제 변경 시 새 버전 파일을 추가하고 매니페스트만 갱신한다.

```jsonc
// rules/2026-03.json
{
  "version": "2026-03",
  "effectiveFrom": "2026-03-01",
  "stressDSR": {
    "stage": 3,
    "surcharge": { "수도권변동": 0.015 }
  },
  "ltv": { "수도권_무주택": 0.7, "생애최초": 0.8 },
  "absoluteCap": { "수도권_주택구입": 600000000 },
  "dsrLimit": { "은행": 0.4 },
  "safetyThreshold": { "safe": 0.25, "caution": 0.35 },
  "policyLoans": [
    {
      "id": "디딤돌",
      "eligibility": { "무주택": true, "연소득상한": 60000000, "주택가격상한": 500000000 },
      "maxAmount": 250000000,
      "rate": 0.032
    }
    // 보금자리론, 신생아특례도 동일 스키마로 추가
  ]
}
```

위 수치는 스키마를 보이기 위한 예시다. **실제 값은 구현 시 각 상품의 공식 고시 기준으로 채운다.**

**적용 범위: 수도권·규제지역 기준.** 구현된 룰셋(`rules/2026-03.json`)은 위 예시와 달리 지역 키를
두지 않고 `ltv` · `absoluteCap` · `stressDSR.surcharge`를 스칼라로 눌러 담는다. MVP 범위가 수도권
한정이라 지역 축이 필요 없었기 때문이다. 그 결과 룰셋만 보면 전국에 통용되는 값처럼 보이므로,
파일 최상단 `_scope` 필드와 `Rules` 인터페이스 주석에 범위를 명시해 둔다.
**다른 지역 지원은 값 교체가 아니라 스키마에 지역 축을 추가하는 별도 작업이다.**
정책대출은 소득·자산·주택가격·자녀수 등 조건 축이 상품마다 달라, `eligibility`를
조건 키-값 집합으로 두고 엔진이 일반적으로 평가하는 구조로 간다.

화면 하단에 **"2026년 3월 규제 기준으로 계산됨"** 을 항상 표시한다.

## 8. 랭킹 (`src/lib/ranking/`)

1. **필터**: `단지 평형 시세 <= 실구매력`
   (실구매력이 이미 대출한도와 부대비용을 모두 반영한 값이므로 여기서 다시 차감하지 않는다)
2. **정렬**: 상환부담률 오름차순 (낮을수록 위)
3. **신호등**:

| 배지 | 조건 |
|---|---|
| 🟢 안전 | 상환부담률 < 25% |
| 🟡 주의 | 25% ~ 35% |
| 🔴 위험 | > 35%, 또는 스트레스 시나리오에서 40% 초과 |

임계값은 룰셋 파일에서 읽는다.

| 1 | 입력 위저드 (3스텝) | ① 보유 현금 ② 소득·기존 부채 ③ 주택 상황(무주택/갈아타기) |
| 2 | 예산 결과 | "6.8억까지 대출 가능, 부대비용 4,100만원 → 실구매력 6.4억"<br>**4개 한도 중 무엇에 걸렸는지 반드시 명시** |
| 3 | 단지 목록 | 상환부담률 오름차순, 신호등 배지, 지역 필터 |
| 4 | 단지 상세 | 시세 추이, 상환 시뮬레이션, 네이버부동산 딥링크 |
| 5 | 리포트 | 인쇄 CSS로 PDF 출력 (배우자·부모님 설득용) |

**2번 화면의 "어느 한도에 걸렸는가"가 이 제품에서 가장 중요한 정보다.**
"6억 캡에 걸렸다"와 "DSR에 걸렸다"는 사용자가 취해야 할 다음 행동이 완전히 다르다.

## 10. 에러 처리

| 상황 | 처리 |
|---|---|
| 국토부 API 실패 | 재시도 + 백오프. **부분 실패 시 이전 스냅샷 유지** — 깨진 데이터를 배포하느니 하루 묵은 데이터가 낫다 |
| 데이터 로드 실패 (브라우저) | 재시도 버튼 + 명확한 안내 |
| 결과 0개 | 억지로 채우지 않는다. "현재 조건으로는 수도권에서 구매 가능한 단지가 없습니다" + 무엇을 바꾸면 되는지(부채 상환, 예산 조정, 지역 확대) 제시 |
| DSR 이미 초과 | "현재 조건으로는 주담대가 나오지 않습니다"를 정직하게 표시 |
| 룰셋 만료 | 매니페스트 기준일이 오래되면 배너 경고 |

## 11. 테스트 전략

- **재무 엔진 단위 테스트가 전체의 90%.** 공개된 실제 수치로 골든 테스트를 구성한다
  (예: 연소득 1억 · 30년 만기 · 연 4.2% 변동금리 · 스트레스 3단계 → 약 5.7억).
  골든 값은 구현 착수 시 은행권 공식 계산기 또는 금융위 보도자료로 교차 검증한 뒤 고정한다
- **이분 탐색 경계값 테스트**: 6억 캡 근처, LTV 구간 경계, 생애최초 감면 경계, 수렴 실패 케이스
- **파이프라인**: 출력 스키마 검증 + 스냅샷 테스트. 단지 병합 실패율 회귀 감시
- **E2E**: 위저드 완주 시나리오 1개

## 12. 법적 안전장치

- 시세는 **"국토부 실거래가 기반 추정 범위"** 로만 표기한다. 특정 단지의 적정가를 단정하지 않는다
  (감정평가법 저촉 소지 회피)
- 전 화면 면책 문구: "추정치이며 실제 대출한도는 금융기관 심사 결과에 따릅니다"
- 재무정보를 서버에 저장·전송하지 않음을 개인정보 안내에 명시
- 투자 자문으로 해석될 수 있는 표현(수익률 예측, 매수 권유)을 사용하지 않는다

## 13. 디렉토리 구조

```
부동산 saas/
├── rules/                  # 규제 룰셋 (버전별 JSON)
│   └── 2026-03.json
├── scripts/pipeline/       # fetch -> normalize -> aggregate -> emit
├── data/                   # 파이프라인 산출물 (gitignore, CDN 배포)
├── src/
│   ├── lib/finance/        # 순수 재무 엔진 + 테스트
│   ├── lib/ranking/        # 필터 · 정렬
│   ├── components/
│   └── app/                # Next.js (정적 내보내기)
└── docs/superpowers/specs/
```

모노레포로 분할하지 않는다. MVP 규모에서 과설계이며,
`lib/finance`가 순수 함수라 물리적 분리 없이도 경계가 유지된다.

## 14. 후속 제품과의 관계

MVP 완료 후 **부동산 종합 진단**(입지·권리·재무·적정가격)을 별도 제품으로 진행한다.
추천에서 나온 후보 단지를 진단으로 넘기는 퍼널 구조가 된다.

진단 제품 설계 시 반드시 반영할 사항:
**DSCR은 주거용 실거주에 적용되지 않는다.** 임대수익이 0이라 분자가 성립하지 않는다.
구매 유형에 따라 재무 지표를 분기해야 한다.

| 대상 | 지표 |
|---|---|
| 실거주 아파트 | DTI·DSR 기반 상환부담률 + 금리 스트레스 |
| 갭투자 | 전세가율, 역전세 리스크, 보증금 반환 여력 |
| 월세 수익형 | RTI, Cap Rate, DSCR |
