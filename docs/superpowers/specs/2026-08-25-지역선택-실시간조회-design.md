# 예산 확정 → 지역 선택 → 실시간 실거래가 조회 설계

**작성일:** 2026-08-25
**상태:** 브레인스토밍 완료, 사용자 검토 대기
**선행:** 데이터 파이프라인, 룰셋 2026-08, 단지목록(화면 3) — 전부 main

## 1. 왜 하는가

지금은 강남·서초·송파 3개 구만 파이프라인이 미리 집계해 번들에 넣어 두고, 화면은 그 안에서만 필터링한다(`RegionFilter`). 사용자가 실제로 살고 싶은 지역이 이 3개 구 밖이면 이 제품은 아무것도 보여줄 수 없다.

이 스펙은 "예산을 먼저 확정하고, 그다음 전국 어디든 원하는 지역을 골라 그 지역의 실거래가를 즉시 조회"하는 흐름을 다룬다.

## 2. 범위 — 세 개로 쪼갠 것 중 이번 스펙은 A만

요청 전체는 서로 의존관계가 있는 세 하위 프로젝트다:

- **A. 예산 계산 → 지역 선택 → 지역 필터링된 실거래가 조회** — 좌표 불필요. **이 스펙의 범위.**
- **B. 지도에 단지 표시 + 가격 범위** — 지오코딩 필요(키 발급 대기 중, 아직 막혀 있음)
- **C. 도보경로 애니메이션 + 인근 학교 정보** — 지오코딩 + 보행자 경로 API + 통학구역 데이터, 전부 아직 확보 전

B·C는 외부 자원이 도착해야 설계를 시작할 수 있다. 이 스펙은 A만 다루고, B·C는 자원이 준비되면 별도 스펙으로 브레인스토밍한다.

## 3. 화면 흐름 — 단계형 위자드

1. 현금·소득·주택수 등 입력 → "실구매 가능 가격" 확정 (기존 화면 그대로, 바뀌지 않는다)
2. 확정되면 다음 단계로 **광역단체 → 자치구** 2단 선택이 노출된다. 예산을 확정하기 전에는 지역 선택 단계 자체가 보이지 않는다 — "예산 없이 지역부터 고르는" 순서 오류를 화면 구조로 막는다.
3. 자치구를 확정하면 그 구의 실거래가를 즉시 조회해 추천 단지를 보여준다.
4. 결과가 오면 그 결과 안에 실제로 등장한 법정동 이름들로 **행정동 좁히기**(3단계)를 보여준다 — API를 다시 부르지 않고 이미 받은 결과를 걸러낸다(§5 참고).

기존 `RegionFilter`(3개 구 다중 선택 체크박스, 정적 데이터 안에서 필터링)는 이 흐름으로 완전히 교체된다.

**설계 메모(브레인스토밍 이후 다듬은 부분):** 애초 구상은 "광역단체→자치구→행정동을 전부 고른 뒤 조회"였다. 구현 단계에서 두 가지 제약이 드러나 순서를 바꿨다 — (1) 전국 읍면동을 전부 번들에 넣으면 용량이 커진다(§4), (2) 이 프로젝트의 네트워크 가드는 동적 `import(`도 금지해 지역별 정적 청크를 지연 로드하는 흔한 해법을 쓸 수 없다(§7). 동 단위는 국토부 API 자체가 지원하지 않아 애초에 응답을 받은 뒤 걸러야 하므로(§5), "구까지 고르면 바로 조회하고 동은 결과 안에서 좁힌다" 쪽이 자연스럽고 두 제약도 함께 피해간다. 사용자가 얻는 결과(원하는 동까지 좁혀 볼 수 있다)는 그대로다.

## 4. 지역 데이터

지금 저장소엔 지역코드가 3개뿐이라 전국 단위 선택기를 만들려면 법정동 코드 데이터가 필요하다.

**출처:** 공공데이터포털의 "국토교통부_전국 법정동"(https://www.data.go.kr/data/15063424/fileData.do) — CSV, 컬럼 `법정동코드,시도명,시군구명,읍면동명,리명,순번,생성일자`, 20,561행(2026-07-29 기준). 로그인 없이 다운로드 가능. 학교·지하철 데이터(`data/sources/schools.csv`, `subway-stations.csv`)와 같은 방식으로 원본을 받아 컬럼만 추려 `data/sources/legal-dong-codes.csv`로 저장소에 둔다.

**번들에는 시/도+시/군/구 단위만 넣는다(§3의 설계 메모 참고).** 원본 20,561행(읍면동·리 단위까지 포함한 전체 이력)을 `법정동코드`의 앞 5자리로 묶어 중복 제거하면 시/군/구 약 250여 개로 줄어든다 — 이 정도는 번들에 넣어도 부담이 없다. 파이프라인 스크립트(`scripts/pipeline/region-codes.ts`)가 이 축약을 수행해 `data/legal-dong-codes.json`을 만든다.

## 5. 백엔드 API

**엔드포인트:** `GET /api/complexes?regionCode=11680&dong=답십리동` — Vercel 서버리스 함수(`/api/complexes.ts`) 하나. `dong`은 선택값이다(§3에 따르면 프론트엔드는 첫 조회 때 넘기지 않고, 결과를 받은 뒤 같은 지역을 `dong`과 함께 다시 부르거나 클라이언트에서 걸러도 되지만 — 이 구현에서는 **클라이언트에서 거른다**, 재조회를 피하기 위해서다. API 자체는 재사용성을 위해 `dong` 파라미터를 계속 지원한다). 무료(Hobby) 티어로 시작하고, 별도 캐시 서비스는 두지 않는다(사용자 결정) — 매 요청마다 국토부 API를 라이브로 호출한다.

**처리 흐름 (전부 메모리에서, 디스크에 아무것도 쓰지 않는다):**

1. 선택된 `regionCode`로 최근 **12개월**치를 병렬로 `fetchAllPages`(`scripts/pipeline/fetch.ts`, 이번에 export로 공개한다) 호출해 재사용한다.
   - 화면에 실제로 보이는 창은 6개월(`AGGREGATION_WINDOW_MONTHS`)이지만, `aggregate()`(`scripts/pipeline/aggregate.ts`)가 저신뢰 판정 등에 12개월 창을 함께 쓰도록 이미 설계돼 있다. 6개월만 받으면 이 판정이 배치 파이프라인과 다르게 나와 두 경로가 은근히 갈라진다 — 그래서 12개월을 그대로 유지한다.
   - 배치 파이프라인은 지역이 여럿이라 순차+200ms 쓰로틀이 필요했지만, 여기는 지역 하나뿐이라 12개월을 병렬로 호출해도 무리가 없다.
2. `normalizeAll` → `aggregate()` 그대로 재사용해 `ComplexUnit[]` 생성.
3. `dong` 파라미터가 있으면 `legalDongName`으로 한 번 더 필터링.
4. `toEmittedUnit()`(`scripts/pipeline/emit.ts`)으로 `medianPrice`·`changeRate*`(감정평가법·수익률예측 금지 필드, §6 참고)를 제거.
5. `regionCode`가 규제지역 목록(§5-1)에 있는지 조회해 응답에 함께 싣는다.

**응답 형식:**

```json
{
  "units": [ /* EmittedComplexUnit[], data/complexes.json과 같은 모양 */ ],
  "isRegulatedArea": true
}
```

`isRegulatedArea`는 `true | false | null`이다. `null`은 "이 지역이 아직 목록에 없어 모른다"는 뜻이다(§5-1).

**에러 처리:** 국토부 API 실패(4xx/5xx/타임아웃)는 200+빈 배열이 아니라 명시적으로 다른 상태코드를 반환한다(§7 참고). 에러 메시지에 `PUBLIC_DATA_API_KEY`가 노출되지 않도록 기존 `redactKey`(`fetch.ts`)를 재사용한다.

### 5-1. 규제지역 목록을 백엔드가 관리한다

지금 `rules/2026-08.json`의 `regulatedRegionCodes`는 딱 3개 구(강남·서초·송파)만 들어있고, 이 목록은 **프론트엔드 번들에 구워 넣는 룰셋 파일**이다. 지역 선택이 전국으로 넓어지면, 목록에 없는 지역을 "비규제"로 잘못 단정하는 위험이 생긴다(LTV 한도를 최대 30%p 과대평가하는 방향 — `ProfileForm.tsx`가 "모르면 규제지역"을 기본값으로 둔 것과 정반대다).

**해결:** 규제지역 목록을 프론트엔드 번들에서 떼어내 백엔드 전용 파일 `api/_data/regulated-regions.json`으로 옮긴다.

```json
{
  "regulated": ["11650", "11680", "11710"],
  "nonRegulated": []
}
```

- `regionCode`가 `regulated`에 있으면 응답의 `isRegulatedArea: true`
- `nonRegulated`에 있으면 `false`
- 둘 다 아니면 `null`("모른다")

이 파일은 **백엔드 코드에만 존재**하고 프론트엔드 JS에는 실리지 않는다. 규제지역 지정이 바뀌면 이 파일만 고쳐 백엔드를 재배포하면 되고(Vercel 배포는 수 초), 프론트엔드를 다시 빌드할 필요가 없다. 지금은 파일 하나로 충분하고, 나중에 배포 없이 즉시 갱신하고 싶어지면 Vercel Edge Config(무료 티어 있음)로 옮길 수 있다.

**목록 내용 자체(전국 어느 구가 실제로 규제지역인지)는 이 스펙이 채우지 않는다.** 국토부 고시를 정확히 반영해야 하는 사안이라, 지금 아는 3개 구만 넣어 두고 전국 목록은 별도로 검증해 채워야 한다. 그때까지 목록에 없는 지역은 전부 `null`로 응답하고, 화면은 그 지역들에서 안전한 가정(규제지역)을 그대로 유지한다.

## 6. 시세 표기 원칙은 그대로 승계

이 스펙은 §3(단지목록 설계)의 "시세는 범위로만 표기한다"·"변동률을 화면에 내지 않는다" 원칙을 그대로 물려받는다. `toEmittedUnit()`을 거치는 것 자체가 이 원칙을 구조로 강제한다 — 라이브 API 응답이라고 다른 규칙을 적용하지 않는다.

## 7. 프론트엔드 상태 처리 — "조회 실패"와 "결과 없음"을 구분한다

지역을 선택하면 4가지 상태 중 하나가 되고, 각각 **완전히 다른 문구·다른 UI**로 보여준다. 이 앱이 이미 곳곳에서 지키는 원칙(`LocationFacts`의 "아직 위치를 몰라요" vs "반경 안에 0곳"과 같은 패턴)과 같은 이유다 — "모르는 것"과 "확인했더니 없는 것"을 절대 같은 문구로 보여주지 않는다.

| 상태 | 화면 |
|---|---|
| **조회 중** | 로딩 표시. 결과 목록·빈 안내 둘 다 아직 그리지 않는다 |
| **조회 실패**(네트워크·국토부 API 장애) | "지금 실거래가를 불러오지 못했어요" + **다시 시도** 버튼. 목록은 아예 렌더링하지 않는다 |
| **조회 성공, 0건** | 기존 `EmptyMessage`(§10, 단지목록 스펙)에 "지역 실거래가 자체가 0건"이라는 사유를 추가 |
| **조회 성공, 결과 있음** | 기존 `ComplexList` 그대로. 동 좁히기 UI가 함께 뜬다(§3) |

**구현:** `useRegionComplexes(regionCode)` 훅이 `{ status: "idle" | "loading" | "error" | "success", units, isRegulatedArea, error }` 형태로 상태를 들고, `App.tsx`가 `status`로 위 넷을 명시적으로 가른다. `units`가 빈 배열인지만으로 판단하지 않는다 — 실패 시 빈 배열을 폴백값으로 두면 "0건"과 구분이 사라진다. API 핸들러도 실패를 성공(200)과 다른 상태코드로 응답해 이 구분이 HTTP 레벨에서부터 시작되게 한다.

`isRegulatedArea`가 `true`/`false`로 오면 프로필의 `isRegulatedArea` 필드를 그 값으로 설정한다(기존 `handleRegionChange`와 같은 동작). `null`이면 프로필을 건드리지 않는다 — 기존 가정이 그대로 유지된다.

## 8. 네트워크 가드를 좁힌다

`src/no-network.test.ts`는 이 제품의 핵심 약속("입력한 재무정보는 이 브라우저를 벗어나지 않는다")을 지키려고 `src/` 안 모든 네트워크 호출(`fetch` 포함)을 전면 금지하는, 소스를 직접 스캔하는 가드다. 이 스펙이 요구하는 라이브 조회는 이 가드와 정면으로 부딪힌다.

**해결: 전면 금지를 유지하되, 파일 하나만 정교하게 예외로 둔다.**

- 새 모듈 `src/lib/regionQuery.ts` **딱 하나**만 `fetch`를 쓸 수 있다. 나머지 `src/` 전체는 지금처럼 네트워크 호출이 원천 금지된 채로 남는다.
- 이 파일은 `regionCode`·`dong`(문자열)만 인자로 받아 **상대경로** `/api/complexes`로만 요청한다 — 하드코딩된 same-origin 경로라 외부 호스트로 나갈 수 없다.
- 새 가드 테스트가 이 파일의 소스를 직접 스캔해서 **재무 필드 이름(`cash`·`annualIncome`·`existingDebtAnnualPayment`·`ownedHomeCount`·`isFirstTimeBuyer`·`isRegulatedArea` 등)이 단 하나도 등장하지 않는지** 확인한다 — 문자 그대로 등장하지 않으면 보낼 방법도 없다는, 기존 가드와 같은 "구조로 증명" 방식이다.
  - `isRegulatedArea`는 이 파일이 **응답에서 받아서 반환은 하지만**, 요청을 만드는 데는 쓰지 않는다 — 그래서 이 필드 이름이 요청 URL 구성 부분에 등장하지 않는지만 확인하면 된다(반환 타입 선언에는 당연히 등장한다 — 가드는 요청을 만드는 코드 블록만 스캔한다. 정확한 스캔 범위는 구현 계획에서 정한다).
- `no-network.test.ts`의 전면 스캔은 **이 파일 하나만** 제외 목록에 추가한다. 그 예외 파일이 정확히 하나만 존재하는지(다른 파일이 몰래 같은 예외를 타지 않는지)도 함께 잠근다 — 지금 이 테스트가 자기 자신(`no-network.test.ts`)에 대해 이미 하는 것과 같은 패턴이다.
- `scripts/pipeline/`이 스캔에서 빠지는 이유("사용자 데이터를 아예 보지 않는 빌드 타임 도구")와 이번 예외의 이유는 다르다 — 이번엔 런타임에 사용자가 고른 지역코드가 실제로 나간다. 그래서 "안 본다"가 아니라 "재무 필드가 없다"로 증명해야 한다.

**화면 문구:** "입력한 재무정보는 이 브라우저를 벗어나지 않아요"(`App.tsx:290`)는 지역코드가 재무정보가 아니므로 엄밀히는 그대로 참이지만, 오해를 막기 위해 한 줄을 덧붙인다 — "지역 실거래가 조회에는 고른 지역 코드만 서버로 전송돼요."

## 9. 하지 않는 것

- **B(지도 표시)·C(도보경로·학교)** — 별도 스펙. 지오코딩·통학구역·보행자 경로 API가 준비되면 진행한다.
- **캐싱** — 무료 티어 유지가 우선이라 이번엔 두지 않는다. 사용량이 늘어 국토부 API 쪽 지연·요청 제한이 문제가 되면 그때 다시 검토한다.
- **전국 규제지역 목록 채우기** — §5-1의 파일 구조·배선만 만든다. 실제 전국 목록 조사는 범위 밖이다.
- **수도권 범위 문구 확장** — 화면 부제의 "· 수도권"은 이 스펙 범위 밖이다(전국 조회가 가능해지면 이 문구도 손봐야 하지만, 별도로 처리한다).
- **기존 정적 3개 구 데이터 유지 여부** — 이 스펙 완료 시 `RegionFilter`가 새 흐름으로 완전히 교체되므로, 배치 파이프라인 산출물(`data/complexes.json`)을 계속 번들에 넣을지는 구현 단계에서 정한다(테스트 픽스처로는 남을 수 있다).

## 10. 테스트 전략

기존 파이프라인 테스트 문화(순수 함수 단위 테스트 + 소스를 직접 훑어 아키텍처 원칙을 잠그는 가드 테스트)를 그대로 따른다.

1. **라이브 조회 오케스트레이션 함수**(fetch→normalize→aggregate→toEmittedUnit→규제지역 조회, 지역 하나·12개월) — mocked fetch로 단위 테스트. 같은 원시 거래 데이터를 배치 파이프라인 경로와 라이브 경로 양쪽에 먹여 결과가 똑같이 나오는 패리티 테스트를 추가한다.
2. **API 핸들러(`/api/complexes`)** — 성공(200+목록) / 성공+0건(200+빈배열) / 국토부 실패(다른 상태코드) 세 응답이 실제로 다른지 확인. `isRegulatedArea`가 목록에 있는/없는 지역에서 각각 true·false·null로 오는지 확인. `PUBLIC_DATA_API_KEY`가 에러 메시지에 노출되지 않는지(`redactKey` 재사용) 확인.
3. **가드 테스트**: API 응답이 `medianPrice`·`changeRate*`를 절대 포함하지 않는다 — 소스가 `toEmittedUnit`을 반드시 거치는지 직접 확인.
4. **네트워크 가드**: `src/lib/regionQuery.ts` 하나만 `fetch` 예외이고, 그 파일에 재무 필드 이름이 등장하지 않으며, 그 파일이 상대경로 `/api/complexes` 외 다른 곳으로 요청하지 않는다.
5. **지역 선택기 컴포넌트**: 광역단체→자치구 선택이 올바르게 좁혀지는지, 법정동코드 데이터셋과 어긋나지 않는지. 결과가 온 뒤 동 좁히기가 실제 등장한 법정동만 보여주는지.
6. **`useRegionComplexes` 훅**: loading/error/empty/success 네 상태가 서로 확실히 구분되는지 — 특히 "실패했는데 목록이 빈 배열로 렌더링되는" 회귀를 잠그는 테스트. `isRegulatedArea`가 null일 때 프로필을 건드리지 않는지.
7. **App 통합 테스트**: 예산 확정 전에는 지역 선택 단계가 보이지 않는다 → 예산 확정 → 지역 선택 단계 노출 → 지역 선택 → (API 모킹) 네 상태 각각이 화면에 맞게 뜨는지.
8. **법정동코드 데이터셋 검증**: 학교·지하철 데이터처럼 행 수·컬럼 형식을 원본과 대조하는 스크립트 테스트.

## 11. 완료 기준

- 예산을 확정해야 지역 선택 단계가 나타난다
- 광역단체 → 자치구 선택으로 전국 아무 구나 고를 수 있고, 조회 결과 안에서 행정동까지 좁힐 수 있다
- 선택한 지역의 실거래가를 국토부 API에서 즉시 조회해 보여준다
- 조회 실패·결과 0건·결과 있음이 서로 다른 화면으로 명확히 구분된다
- 시세 범위·변동률 미표시 원칙이 라이브 응답에서도 그대로 지켜진다
- 규제지역 목록이 백엔드 전용 파일로 관리되고, 프론트엔드 번들에는 실리지 않는다. 목록에 없는 지역은 기존 가정을 건드리지 않는다
- `no-network.test.ts`의 전면 금지가 `src/lib/regionQuery.ts` 하나만 빼고 그대로 유지되고, 그 파일에 재무 필드가 등장하지 않는다는 가드가 통과한다
- 화면 부제에 지역코드 전송 사실이 명시된다
- 전체 스위트 통과, 타입체크 클린
