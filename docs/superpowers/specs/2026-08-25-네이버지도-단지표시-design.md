# 네이버지도에 추천 단지 표시 설계

**작성일:** 2026-08-25
**상태:** 브레인스토밍 완료, 사용자 검토 대기. 지오코딩은 정부 좌표제공 API(승인 대기 중이라 느림) 대신 **네이버 Geocoding API**로 바꿨다 — 이미 갖고 있는 네이버지도 애플리케이션에 같이 딸려 있어 별도 승인 없이 바로 쓸 수 있다. 키는 `.env`에 이미 들어있다. **막혀 있던 것이 풀려 바로 구현 계획으로 넘어갈 수 있다.**
**선행:** 지역 선택·실시간 조회(화면 A) — main

## 1. 왜 하는가

지역 선택 후 목록으로 단지를 보여주는 화면(A)은 이미 있다. 이 스펙은 그 위에 지도를 더해, 사용자가 단지의 실제 위치를 보고 아이콘을 눌러 간단한 정보(이름·가격 범위·거래 건수)를 확인할 수 있게 한다.

## 2. 범위 — B만, C는 아직

브레인스토밍 초반에 나눈 세 하위 프로젝트(A/B/C) 중 이 스펙은 **B(지도 표시)만** 다룬다. C(도보경로·학교)는 보행자 경로 API·통학구역 데이터가 준비되면 별도로 진행한다.

## 3. 전체 흐름

1. 지역 조회가 성공해 목록·예산 결과가 뜬다(화면 A, 변경 없음).
2. 목록 아래에 지도 영역이 나타난다. 처음엔 "지도를 불러오고 있어요" 상태이고, 좌표 조회가 끝나면 좌표를 아는 단지만 아이콘으로 찍힌다. 좌표를 못 찾은 단지는 조용히 지도에서 빠진다 — 추측 좌표를 만들지 않는다(`data/README.md`의 기존 원칙과 같다: "대체 좌표를 만들지 않는다").
3. 아이콘을 누르면 그 단지의 이름·가격 범위·거래 건수(목록 행과 같은 정보, 이미 프론트엔드가 갖고 있음)가 팝업으로 뜬다. **단일 "적정가" 숫자는 여기서도 내지 않는다** — §6 참고.
4. 행정동으로 좁히면(화면 A의 기능) 지도 아이콘도 같이 좁혀진다 — 지도는 화면 A가 이미 필터링한 `dongFilteredUnits`를 그대로 받는다.
5. 지도 로딩은 **목록이 뜬 다음** 별도로 진행한다 — 지도 때문에 이미 검증된 목록·예산 흐름이 느려지지 않게 하려는 것이다.

## 4. 좌표를 어떻게 구하는가

**단지 좌표는 지금 어디에도 없다.** `data/location.json`의 `complexes[]`는 처음부터 빈 배열이었고(지오코딩 API가 없어서), 라이브 조회 결과(`EmittedComplexUnit`)에도 좌표 필드가 없다. 이 스펙이 그 빈자리를 채운다.

**새 엔드포인트:** `GET /api/geocode?regionCode=11680&dong=답십리동`

처리 흐름:
1. 최근 **1개월**치만 가볍게 조회한다(화면 A의 `/api/complexes`가 쓰는 12개월과 다르다 — 건물 주소는 어느 달 거래든 같으므로 가장 가벼운 조회로 충분하다).
2. 조회된 거래에서 단지별 대표 주소를 하나씩 뽑는다(`RawTrade.address`, 지금은 파이프라인 어디서도 화면에 내지 않고 저장만 하던 필드). 네이버 Geocoding은 지번·도로명 주소를 문자열로 받으므로, `RawAddress`의 필드(`roadNm`·`jibun` 등)를 조합해 하나의 주소 문자열로 만든다 — 정확한 조합 규칙은 구현 계획에서 정한다.
3. 주소를 캐시에서 찾는다. **주소는 거의 영구적이므로 캐시가 절대 낡지 않는다** — 화면 A가 캐싱을 미룬 이유(가격은 매달 바뀐다)가 여기엔 적용되지 않는다. 캐시 미스만 **네이버 Geocoding API**(`GET https://naveropenapi.apigw.ntruss.com/map-geocode/v2/geocode?query=...`)를 호출한다. 인증은 국토부 API와 다르다 — URL 쿼리에 담는 `serviceKey` 하나가 아니라, 요청 헤더 `x-ncp-apigw-api-key-id`(Client ID)·`x-ncp-apigw-api-key`(Client Secret) 두 개를 함께 보낸다. 키 유출 방지(`redactKey`에 해당하는 조치)도 이 헤더 두 값 모두를 가려야 한다. 주소를 못 찾으면 `addresses: []`(빈 배열)로 오는 것으로 간주하고 방어적으로 처리한다 — "찾았는데 좌표가 이상하다"와 "아예 못 찾았다"를 구분해서, 후자는 조용히 그 단지를 빼고(§7) 전자 같은 경우는 없다.
4. 새로 구한 좌표를 캐시에 저장한다.
5. `{ complexKey, lat, lon }[]`만 응답한다. **주소 자체는 응답에 실리지 않는다** — `data/README.md`의 기존 원칙("주소를 내지 않는다. 지오코딩 입력으로만 쓰고 화면에 오지 않는다")을 그대로 지킨다. 이 원칙 때문에 `/api/complexes`가 아니라 별도 엔드포인트로 가고, 그 엔드포인트도 지역코드만 받아 서버 안에서 주소를 다시 찾는다(§4-1의 대안 A 대신 B를 택한 이유).

**캐시:** ~~Vercel KV~~ → **Upstash Redis**(Vercel 마켓플레이스 연동, 무료 티어). Vercel KV는 2024년 12월부로 단종되고 기존 데이터는 Upstash Redis로 자동 이전됐다 — 지금은 신규 프로젝트에 Vercel Storage 탭에서 "Upstash for Redis" 연동을 추가하는 방식이다. key는 주소, value는 좌표. 국토부 실거래가 캐싱과 달리 만료(TTL) 없이 영구 보관한다. 연동을 추가하면 `KV_REST_API_URL`·`KV_REST_API_TOKEN` 환경변수가 자동으로 채워진다(이름은 옛 Vercel KV 시절 그대로 유지됨). **사용자 액션 필요**: Vercel 대시보드 → 프로젝트 → Storage 탭 → Marketplace → Upstash for Redis 추가.

**환경변수(이미 `.env`에 있음):** `NAVER_GEOCODE_CLIENT_ID`·`NAVER_GEOCODE_CLIENT_SECRET`(서버 전용, `PUBLIC_DATA_API_KEY`와 같은 자리). 지도 표시용 `VITE_NAVER_MAP_CLIENT_ID`(§5)와는 별개 변수다 — 값은 같을 수 있지만 쓰이는 자리가 다르다(브라우저 vs 서버).

### 4-1. 검토했던 대안

- **대안 A(기각):** `/api/complexes` 응답에 단지별 주소를 실어 프론트가 `/api/geocode`에 그대로 넘기는 방식. 추가 API 호출이 없어 효율적이지만, "주소는 화면에 안 낸다"는 기존 원칙을 처음으로 깬다. 사용자가 이 원칙과의 일관성을 이유로 기각하고 대안 B를 골랐다.
- **대안 B(채택):** 위 §4의 방식. 지역당 국토부 실거래가 API 호출이 하나(1개월치) 늘지만, 주소가 브라우저에 한 번도 닿지 않는다.
- **지오코딩 제공자: 정부 좌표제공 API → 네이버 Geocoding API로 교체.** 애초 계획은 행정안전부 좌표제공 API였으나 승인이 느려(vs. 도로명주소 API는 즉시 발급) 막혀 있었다. 이미 갖고 있던 네이버지도 애플리케이션에 Geocoding이 같은 상품으로 포함돼 있어(§5의 지도 표시와 같은 NCP "Maps" 서비스), 별도 승인 없이 바로 쓸 수 있다는 것을 확인해 교체했다. 서버 쪽 설계(주소는 캐시까지만, 응답엔 안 실음, 캐시는 영구 보관)는 제공자와 무관하게 그대로 유효하다.

## 5. 프론트엔드

**네이버지도 스크립트를 불러오는 문제.** 네이버지도를 화면에 띄우려면 `<script src="https://oapi.map.naver.com/openapi/v3/maps.js?ncpKeyId=...">` 같은 태그로 네이버가 만든 자바스크립트를 통째로 실행해야 한다(쿼리 파라미터 이름이 `ncpKeyId`다 — 옛 문서의 `ncpClientId`는 지금은 안 쓰인다). 이건 `src/no-network.test.ts`가 지키는 "재무정보가 네트워크를 탈 경로가 코드상 존재하지 않는다"는 약속과 정면으로 부딪힌다 — `regionQuery.ts`(우리 서버로 지역코드만 보내는 `fetch` 하나)보다 신뢰 경계가 훨씬 크다. 우리가 통제하지 못하는 서드파티 코드가 브라우저 안에서 실행되기 때문이다.

**해결(기존 패턴을 그대로 따른다):** `src/lib/loadNaverMaps.ts` **딱 하나**의 파일만 이 스크립트 삽입을 할 수 있다. `no-network.test.ts`에 새 가드 테스트를 추가해 — 이 파일이 정확히 하나만 존재하는지, 하드코딩된 네이버지도 URL 하나 외에 다른 곳으로는 못 나가는지, 재무 필드 이름이 등장하지 않는지 — `regionQuery.ts` 때와 같은 방식으로 소스를 직접 스캔해 증명한다.

**네이버 클라이언트 ID는 비밀키가 아니다.** `PUBLIC_DATA_API_KEY`와 달리 프론트엔드 코드에 그대로 노출되는 게 정상이다(네이버는 대신 콘솔에 등록한 도메인으로만 동작하게 막는다). 그래서 이 값은 백엔드로 감쌀 필요가 없다 — 배포 도메인을 네이버 클라우드 플랫폼 콘솔에 등록하기만 하면 된다.

**새 조각들:**
- `useComplexCoordinates(regionCode, dong)` 훅 — `/api/geocode`를 호출해 idle/loading/success 상태를 든다. `useRegionComplexes`와 같은 패턴이다.
- `ComplexMap` 컴포넌트 — 좌표가 있는 단지만 아이콘으로 그리고, 클릭 시 이름·가격 범위·거래 건수 팝업을 띄운다.

## 6. 시세 표기 원칙은 그대로 승계

지도 팝업도 화면 A·기존 단지목록 스펙의 원칙을 그대로 물려받는다 — `medianPrice`·`changeRate*`를 내지 않고, 가격은 범위(`minPrice`~`maxPrice`)와 거래 건수로만 말한다. 지도라는 새 화면이라고 다른 규칙을 적용하지 않는다.

## 7. 하지 않는 것

- **C(도보경로·학교)** — 별도 스펙.
- **단일 "적정가" 추정** — §6. 감정평가법 저촉 회피 원칙은 이 스펙에서도 그대로다.
- **좌표 없는 단지의 대체 표시** — 못 찾으면 그냥 안 그린다. 근처 단지 좌표로 채우거나 법정동 중심점으로 대신하지 않는다(`data/README.md`의 기존 원칙).
- **동적 클러스터링·경로 최적화 등 지도 고급 기능** — YAGNI. 아이콘 표시 + 클릭 팝업까지만.

## 8. 테스트 전략

1. **`/api/geocode` 핸들러**: 캐시 히트/미스 각각 확인. 좌표를 못 찾은 단지는 결과 배열에서 빠지는지(가짜 좌표로 채우지 않는지). 응답에 주소 필드가 없는지. 네이버 Geocoding 실패 시 `NAVER_GEOCODE_CLIENT_SECRET`이 에러 메시지에 노출되지 않는지.
2. **네트워크 가드**: `loadNaverMaps.ts`가 정확히 하나만 예외이고, 하드코딩된 네이버지도 URL 외 다른 곳으로 요청하지 않으며, 재무 필드 이름이 등장하지 않는지 — `regionQuery.ts` 가드 테스트와 같은 패턴.
3. **`useComplexCoordinates` 훅**: idle/loading/success 상태가 서로 구분되는지.
4. **`ComplexMap` 컴포넌트**: 좌표 없는 단지는 아이콘이 안 뜨는지, 아이콘 클릭 시 올바른 단지 정보가 뜨는지, 동 좁히기와 연동되는지.
5. **캐시 정합성**: 같은 주소를 두 번 조회하면 네이버 Geocoding API를 한 번만 부르는지(캐시가 실제로 절약하는지).

## 9. 완료 기준

- 지역 조회 성공 후, 목록이 먼저 뜨고 지도는 별도로 이어서 채워진다
- 좌표를 아는 단지만 지도에 아이콘으로 뜨고, 클릭하면 이름·가격 범위·거래 건수가 뜬다
- 단일 적정가 숫자는 지도에도 없다
- 네이버 Geocoding API로 보내는 주소가 브라우저까지 도달하지 않는다(서버 안에서만 쓰인다)
- `no-network.test.ts`의 전면 금지가 `regionQuery.ts`(+그 테스트)·`loadNaverMaps.ts`(+그 테스트) 넷만 빼고 그대로 유지된다
- 같은 단지를 반복 조회해도 네이버 Geocoding API가 한 번만 불린다(캐시 동작)
- 전체 스위트 통과, 타입체크 클린
