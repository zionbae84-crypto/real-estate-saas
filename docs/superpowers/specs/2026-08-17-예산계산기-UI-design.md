# 예산 계산기 UI — 설계 문서 (Plan C)

- **작성일**: 2026-08-17
- **상태**: 승인됨 (구현 계획 수립 대기)
- **부모 스펙**: `docs/superpowers/specs/2026-08-16-예산기반-부동산-추천-design.md`
- **선행 완료**: Plan A (재무 엔진) — `src/lib/finance/`, 254 테스트 통과

---

## 1. 한 줄 정의

사용자가 현금·소득·부채를 입력하면 실구매 가능 가격과 그것을 막고 있는 제약을 보여주고,
가격 슬라이더로 **"얼마짜리를 사면 얼마나 무리인가"** 를 손으로 만져볼 수 있게 하는 단일 페이지 웹앱.

## 2. 범위

부모 스펙 9절의 화면 1~2번만 구현한다. 화면 3~5번(단지 목록·상세·리포트)은 후속이다.

이 범위는 **단지 데이터를 전혀 필요로 하지 않는다.** 따라서 Plan B(데이터 파이프라인)와
완전히 독립적으로 만들고 배포할 수 있다.

### 범위 밖 (하지 않음)

- 단지 목록·단지 상세 — Plan B의 데이터가 필요하다
- PDF·인쇄 리포트 — 부모 스펙 9절 5번, 후속
- 계정·서버·저장소 — 부모 스펙의 무계정 원칙 유지
- 다국어, 애널리틱스, 외부 폰트 — 네트워크 요청 0을 유지하기 위해 의도적으로 제외

## 3. 부모 스펙에서 변경된 결정

| 항목 | 부모 스펙 | 이 스펙 | 이유 |
|---|---|---|---|
| 프레임워크 | Next.js 정적 내보내기 | **Vite + React** | 화면 2개·데이터 페칭 0·라우팅 없음. Next.js는 서버 프레임워크를 가져와 서버 기능을 전부 끄는 모양이 된다. Vite 빌드 산출물은 순수 정적 파일이라 "재무정보 미전송"이 구조로 보장된다 |
| 입력 형태 | 3스텝 위저드 | **단일 페이지 폼 + 라이브 결과** | 입력 필드가 6개뿐이고, 엔진이 순수 함수라 즉시 재계산된다. "부채를 갚으면 얼마나 늘지"를 즉석에서 실험하는 것이 이 제품의 핵심 경험인데, 위저드는 그것을 구조적으로 막는다 |

부모 스펙 4절과 9절을 이 결정에 맞게 수정한다.

## 4. 아키텍처

```
[브라우저 단일 페이지 — 서버 없음]

  BuyerProfile 폼
       │  (유효할 때만)
       ▼
  calcAffordablePrice(profile, rules) ──> AffordableResult
       │                                        │
       │                          실구매력 / 걸린 제약 / 부대비용
       │                          정책대출 / 경고
       ▼
  가격 슬라이더 [0 … 실구매력]
       │
       ▼
  calcMaxLoan(price) → calcSafetyScore(loan) → 신호등 + 월 상환액

  localStorage ← 프로필만 저장. 결과는 저장하지 않고 항상 재계산
```

### 룰셋 로딩

`rules/2026-03.json`을 **빌드 타임에 import**하여 번들에 포함한다. 로딩 상태도, 네트워크
요청도 없다. 규제가 바뀌면 재배포하며, 정적 사이트에서는 그것이 곧 배포다.

### 네트워크 요청 0

소스에 `fetch`·`XMLHttpRequest`·외부 URL이 하나도 없다. 폰트는 CDN을 쓰지 않고 시스템 폰트
스택을 쓴다. 부모 스펙의 "재무정보가 네트워크를 탈 경로가 코드상 존재하지 않는다"를 유지한다.
이 성질은 테스트로 고정한다(9절).

## 6. 핵심 컴포넌트

### `MoneyInput` — 가장 위험한 지점

사용자는 억·만원 단위로 생각하지만 엔진은 원 단위 정수를 받는다. 그리고 `Number("1억")`은
`NaN`이다 — 최종 리뷰가 Critical로 잡았던 바로 그 입력이다. 엔진에 `assertValidProfile`
가드가 있지만, **UI가 애초에 `NaN`을 만들지 않는 것이 1차 방어선이다.**

요구사항:

- `"3억5000"`, `"35000"`(만원), `"3.5억"`, `"3,5000"`을 모두 받아낸다
- 화면에는 포맷된 형태를 보여주고, 밖으로는 **정수 원**만 내보낸다
- 파싱 실패 시 `NaN`이 아니라 **`null`** 을 내보내며, 폼은 이를 "미입력"으로 취급한다
- 단위 없는 숫자는 **만원**으로 해석한다(한국 부동산 입력 관행)

**만원 기본 해석의 위험과 그 완화.** `50000000`을 "5천만원"이라는 뜻으로 입력하면
만원 해석에서는 5,000억이 된다. 이를 막는 것은 규칙이 아니라 **즉시 되비추기**다:
입력란 바로 아래에 해석 결과를 항상 사람이 읽는 형태로 표시한다
(`50000000` → "5,000억원"). 자릿수를 틀린 순간 눈에 보이므로 규칙을 몰라도 고칠 수 있다.
이 되비추기는 선택적 장식이 아니라 만원 기본 해석을 성립시키는 필수 요소다.

### `BindingExplainer` — 이것이 제품이다

`binding` 값 자체가 아니라 **사용자가 다음에 무엇을 해야 하는지**를 말한다.

| 걸린 제약 | 문구의 요지 |
|---|---|
| `LTV` | 집값의 40~70%까지만 빌려준다(규제지역 무주택 40%, 비규제 70%, 생애최초는 두 지역 모두 70%) → **현금을 더 모으면** 늘어난다 |
| `DSR` | 소득 대비 상환액 한도에 걸렸다 → **기존 부채를 갚으면** 늘어난다 |
| `CAP` | 수도권 주택구입 대출은 6억이 상한이다 → **대출로는 못 늘린다. 현금이 필요하다** |
| `POLICY` | 정책대출을 택할 때의 한도다 → 은행 대출과 비교해 보라 |

각 문구에 실제 금액을 함께 보여준다. `breakdown`의 4개 값을 모두 펼쳐볼 수 있게 하여
2순위 제약이 무엇인지도 드러낸다.

### `PriceSlider` — "사지 말라"고 말하는 순간

범위는 `0 … affordablePrice`, 단위는 엔진이 내보내는 `PRICE_STEP`(10만원).
값이 바뀔 때마다 `calcMaxLoan` → `calcSafetyScore`를 다시 돌려 월 상환액·부담률·신호등을
갱신한다. 순수 함수이므로 즉시 계산된다.

실구매력은 **빌릴 수 있는 한계이지 무리하지 않는 선이 아니다.** 최대치에서 대개 🟡·🔴가
나오며, 사용자가 슬라이더를 내려 🟢이 되는 지점을 직접 찾게 되는 것이 이 화면의 목적이다.

### `PolicyLoanList` — `maxAmount`를 절대 보여주지 않는다

`AffordableResult.matchedPolicyLoans`의 각 항목에서 **`availableAmount`만 금액으로
표시한다.** `loan.maxAmount`는 상품 고시 한도이지 이 구매자가 받을 수 있는 금액이 아니며,
그것을 표시하면 연소득 0원 구매자에게 3.6억을 받을 수 있다고 말하게 된다.
엔진의 타입 주석이 이를 명시하고 있다.

### 필수 입력과 기본값

`BuyerProfile`의 7개 필드(갈아타기 전용 `existingHome`은 제외) 중 사용자가 반드시 채워야
하는 것은 **현금과 연소득 두 개**다. 나머지는 기본값을 두고, 사용자가 바꿀 수 있게 한다.
결과는 두 필수값이 유효해진 순간부터 그려진다.

| 필드 | 기본값 | 근거 |
|---|---|---|
| `cash` | 없음 — **필수** | 이 값 없이는 계산이 성립하지 않는다 |
| `annualIncome` | 없음 — **필수** | 위와 같다 |
| `existingDebtAnnualPayment` | `0` | 부채가 없는 것이 더 흔하다 |
| `status` | `"무주택"` | MVP 타겟의 다수 |
| `isFirstTimeBuyer` | `false` | 잘못 켜두면 한도를 과대평가하므로 꺼진 쪽이 안전하다 |
| `isRegulatedArea` | `true` | 규제지역·비규제지역 LTV가 30%p(40% vs 70%) 갈린다. 잘못 꺼두면 한도를 크게 과대평가하므로, 더 보수적인 규제지역 쪽을 기본값으로 둔다 |
| `exclusiveAreaSqm` | `84` | 수도권 아파트 최빈 평형(국민주택규모) |

`status`가 `"갈아타기"`이면 기존주택 3개 필드가 그 자리에서 펼쳐진다. 이들은 필수가
아니며, 미입력 시 엔진이 경고를 내보낸다(8절).

## 7. 상태와 저장

- `localStorage`에 **프로필만** 저장한다. 결과는 저장하지 않는다
- 키를 버전으로 찍는다(`budget-profile-v1`). 형태가 바뀌어도 옛 데이터로 깨지지 않는다
- **저장된 값을 신뢰하지 않는다.** 사용자가 직접 고칠 수 있는 자리이므로, 읽을 때 다시
  검증하고 이상하면 조용히 빈 폼으로 시작한다

## 8. 에러 처리

| 상황 | 처리 |
|---|---|
| 필수값 미완료 | 결과 영역을 그리지 않는다. "소득을 입력하면 계산됩니다" |
| 갈아타기인데 기존주택 미입력 | 결과는 그리되 엔진이 내보내는 경고를 그대로 표시한다 |
| 실구매력 0원 | **0원을 숫자로 들이밀지 않는다.** "현재 조건으로는 주담대가 나오지 않습니다" + 무엇을 바꾸면 되는지 |
| 엔진이 예외를 던짐 | 에러 경계로 잡는다. 페이지가 죽지 않고 "계산 중 문제 발생 + 입력 초기화" |
| `localStorage` 손상 | 무시하고 빈 폼으로 시작 |
| `warnings` (양도세 미입력 등) | 결과 **위에** 눈에 띄게. 접어두지 않는다 |

엔진 예외는 사실상 버그를 뜻한다(폼이 이미 막았어야 하므로). 그래도 잡는 이유는 재무 계산
화면이 백지가 되는 것이 최악이기 때문이다.

## 9. 테스트 전략

- **`MoneyInput` 파싱이 최우선이다.** `"3억5000"` · `"35,000"` · `"3.5억"` · `""` ·
  `"abc"` · 음수 각각에 대해 무엇을 내보내는지 고정하고,
  **어떤 입력으로도 `NaN`을 내보내지 않는다**를 성질로 검증한다
- `useAffordability`: 프로필 변경 시 결과 갱신, 슬라이더 이동 시 안전성 재계산
- `BindingExplainer`: 4개 제약 각각 올바른 문구와 금액
- 실구매력 0원 경로에서 안내 문구가 뜨는지
- `PolicyLoanList`가 `availableAmount`를 쓰고 `maxAmount`를 금액으로 쓰지 않는지
- 통합 시나리오 1개: 폼에 값을 넣으면 결과와 슬라이더가 나타난다 (Testing Library)
- **네트워크 없음 검증**: 소스에 `fetch`·`XMLHttpRequest`·외부 URL이 없음을 확인

## 10. 데이터 숙제 처리 결과

9절 작성 시점(Plan A 리뷰)에 미해결로 남았던 4개 항목이다. 이후 별도 룰셋 검증 작업에서
전부 조사했고, 상태가 각각 갈렸다. `rules/2026-03.json`과 `src/lib/finance/`가 이미
아래 내용을 반영하고 있다 — **더 이상 이 계획의 범위 밖 숙제가 아니다.**

| 항목 | 상태 | 내용 |
|---|---|---|
| 중개보수 부가가치세 | **해결** | 일반과세자 기준 10%를 `rules.brokerageVatRate`로 반영했다. 캡이 적용된 뒤의 중개보수에 곱해 `CostBreakdown.brokerageVat`로 노출한다. 다만 간이과세자는 부가세를 별도로 받을 수 없으므로, 그 경우 이 값은 실제보다 **과대 추정**일 수 있다 |
| 국민주택채권(옛 항목명: `legalFee`가 못 덮는 채권 할인액) | **부분 해결** | 시가표준액 1,000원당 매입률 구간표(1,000원당 13~31원, 시·도 구간별)는 법령 별표를 확인해 확정했고 `housingBond.brackets`에 반영했다. 다만 매입액을 구하는 데 필요한 두 값 — 매매가 대비 공동주택 공시가격 비율(`assumedPriceToStandardRatio`), 채권 즉시 매도 시 할인율(`assumedDiscountRate`) — 은 여전히 **검증되지 않은 가정치**다. 전자는 단지·연도별로 달라지고, 후자는 매일 변동하며 조사한 출처가 4%~10%로 갈렸다. 두 필드 모두 이름에 `assumed`가 붙어 있고, 화면(`CostBreakdown`)에도 추정치라는 안내 문구가 함께 뜬다 |
| 보금자리론 금리 | **해결 — 플레이스홀더 아님. 단 검증 중 새 문제 발견** | `0.042`가 `baseRate`와 우연히 같은 값이 아니라는 것을 확인했다: 2026-01-01 한국주택금융공사 고시 u-보금자리론 범위(4.00~4.30%) 안에 드는 값이다. 다만 조사 과정에서 2026-07-07 고시가 이 범위를 5.00~5.30%로 올린 사실을 새로 발견했다 — 아래 "새로 발견된 숙제" 참고 |
| `ltv.default = 0.7`(지역 구분 모호성) | **해결이자 결함 발견** | 모호했던 원인은 규제지역과 비규제지역의 LTV가 실제로 다른데 룰셋에 지역 축 자체가 없었기 때문이었다. 확인 결과 규제지역 무주택·처분조건부 1주택자는 **40%**, 비규제(수도권)는 **70%**이며, 생애최초는 두 지역 모두 **70%**다(출처: 금융위원회 「주택시장 안정화 대책」). 룰셋에 `ltv: { regulated: {...}, unregulated: {...} }` 축을 추가하고, `BuyerProfile`에 신규 필수 필드 `isRegulatedArea`(기본값 `true`)를 도입해 분기한다. **이 항목은 단순 미검증이 아니라 실제 결함이었다** — 축이 없던 동안 규제지역 무주택 구매자의 한도가 40% 대신 70%로 계산되어 **30%p 과대평가**되고 있었다 |

### 새로 발견된 숙제: 룰셋 버전 노후화 (미해결, 출시 전 재검토 필요)

위 4개와 별개로, 이번 검증 작업 자체가 새로 만들어낸 문제다. `rules/2026-03.json`은
2026년 3월 시점의 규제를 담고 있는데, 오늘은 2026-08-22다.

- u-보금자리론 금리가 2026-07-07 고시로 **4.00~4.30% → 5.00~5.30%**로 올랐다
- 규제지역 지정이 2026년 7월 **확대**됐다(동탄·기흥·구리 등)

둘 다 `rules/2026-03.json`의 **값**을 바꿔야 하는 사안이지, 코드나 스키마 구조를 바꿀
사안은 아니다. 이 계획(Plan C)의 범위 밖이며, `2026-08` 룰셋 신설을 별도 작업으로
검토해야 한다. 이 항목을 닫지 않고 출시하면, 화면 상단의 "n년 n월 규제 기준" 문구와
실제 규제 사이의 간극을 사용자가 알 길이 없다.

### 출시 게이트 (프로젝트 오너 결정, 2026-08-22)

위 두 항목 중 **보금자리론 금리 노후화**를 이유로 `fix/ruleset-verification` 브랜치
자체를 막지는 않는다 — 대신 **머지는 하되 출시를 게이트한다.**

- 이 룰셋은 버전 `2026-03`으로 고정 스탬프돼 있다. 스탬프가 찍힌 버전 안의 값(여기서는
  `policyLoans[].rate`)을 조용히 고쳐 스탬프를 거짓말하게 만들지 않는다 — 값은
  건드리지 않는다.
- 2026-07-07 한국주택금융공사 고시로 u-보금자리론 금리 범위가
  **4.00~4.30% → 5.00~5.30%**로 올랐다는 사실이 확인돼 있다. `rules.baseRate`와
  `policyLoans[].rate`(보금자리론, `0.042`)는 여전히 옛 고시 기준이다.
  측정한 영향 범위는 `breakdown.POLICY`(정책대출 경로에서 도출한 대출 한도)에
  한정된다 — 낮은 금리를 가정하면 같은 DSR 상환부담 안에서 원금을 더 크게
  잡기 때문에 과대평가 방향이다. 연소득 3천만·매매가 5.5억 프로필 기준으로
  최대 약 **₩16,523,079** 과대평가된다. **헤드라인 실구매력(`affordablePrice`)에는
  영향이 없다** — 이 구간에서는 LTV가 정책대출보다 먼저 걸려 binding이 LTV이기
  때문이다.
- **따라서 `2026-08` 룰셋을 만들어 최신 고시 금리를 반영하기 전까지는 이 브랜치를
  출시하지 않는다.** 머지는 진행하되, 배포 체크리스트에 `2026-08` 룰셋 작성을
  선행 조건으로 건다.
- **규제지역 지정 확대(동탄·기흥·구리 등, 2026년 7월)는 이 게이트에 포함되지
  않는다.** 이 브랜치가 `isRegulatedArea`를 룰셋이 판정하는 값이 아니라 사용자가
  화면에서 직접 체크하는 입력으로 바꿨고, 기본값을 더 보수적인 `true`(규제지역)로
  뒀기 때문이다 — 새로 규제지역에 지정된 지역의 구매자도 체크박스를 켜기만 하면
  정답을 받는다. 지역 목록을 룰셋이나 코드가 대신 판정해주지 않는다는 전제가
  이미 이 설계에 반영돼 있으므로, 지정 확대 자체는 값 교체나 코드 변경을
  요구하지 않는다.
