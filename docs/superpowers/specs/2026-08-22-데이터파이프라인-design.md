# 데이터 파이프라인 — 설계 문서 (Plan B)

- **작성일**: 2026-08-22
- **상태**: 승인됨 (구현 계획 수립 대기)
- **부모 스펙**: `docs/superpowers/specs/2026-08-16-예산기반-부동산-추천-design.md` 5절
- **선행 완료**: Plan A (재무 엔진), Plan C (예산 계산기 UI), 룰셋 검증 반영

---

## 1. 한 줄 정의

국토교통부 실거래가 API에서 수도권 아파트 매매 거래를 수집해, 단지 × 평형별 대표 시세로 집계하고
정적 JSON으로 내보내는 빌드 타임 파이프라인.

## 2. 왜 만드는가

Plan C가 만든 예산 계산기는 "당신은 6억 4,000만원까지 살 수 있습니다"까지 말한다.
그 다음 질문 — **"그럼 어디에 뭘 살 수 있는데?"** — 에 답하려면 단지별 시세가 필요하다.

이 파이프라인은 그 데이터를 만든다. 화면 3~5번(단지 목록·상세·리포트)이 이것을 소비한다.

## 3. 확정된 범위

| 항목 | 결정 |
|---|---|
| 데이터 소스 | 국토교통부 아파트 매매 실거래가 API (공공데이터포털) |
| 인증 | 환경변수 `PUBLIC_DATA_API_KEY`. `.env`는 gitignore |
| 지역 | 설정 파일의 시군구 코드 목록. 초기엔 서울 일부, 검증 후 수도권 전체로 확장 |
| 기간 | **수집** 최근 12개월 / **대표 시세** 최근 6개월 중위값 / **1년 변동률** 12개월 전체 |
| 단지 식별 | **보수적 키 + 이상 신호 리포트** (5절) |
| 산출물 | `data/` 아래 평범한 JSON 세 파일 |

### 범위 밖

- 랭킹 로직(`src/lib/ranking/`) — 후속
- 화면 3~5번(단지 목록·상세·리포트) — 후속
- 다세대·단독주택 — 실거래 데이터 구조가 달라 별도 파이프라인
- 전월세 데이터 — 진단 제품 영역

## 4. 아키텍처

```
scripts/pipeline/
├── fetch.ts       국토부 API → data/raw/{시군구코드}-{년월}.json
├── normalize.ts   raw/ → data/normalized.json
├── aggregate.ts   normalized.json → data/complexes.json
├── emit.ts        + 지역 메타 → data/{complexes,regions,manifest}.json
└── report.ts      이상 신호 → data/report.md
```

각 단계는 **독립 실행 가능한 진입점**이다(`npm run pipeline:fetch` 등). 이전 단계의 출력 파일만
읽으므로 따로 테스트할 수 있다.

**`fetch`만 부정한 단계다.** 네트워크와 파일시스템을 만지는 것은 여기뿐이며,
`normalize`·`aggregate`는 순수 함수라 픽스처만으로 전부 검증된다.

### API 키

`PUBLIC_DATA_API_KEY` 환경변수에서만 읽는다. `.env`는 gitignore에 넣는다.
키가 없으면 `fetch`는 즉시, 발급 방법을 안내하며 실패한다.
**키는 저장소에도 코드에도 들어가지 않는다.**

### 기존 네트워크 금지 약속과의 관계

`src/no-network.test.ts`는 `src/`를 훑고, 파이프라인은 `scripts/`에 산다. 이는 우연이 아니라 의도다.

약속의 내용은 **"사용자 재무정보가 브라우저를 벗어나지 않는다"** 이며, 파이프라인은
**사용자 데이터를 아예 보지 않는 빌드 타임 도구**다. 두 가지가 충돌하지 않는다.

`no-network.test.ts`의 스캔 범위가 `scripts/`를 포함하지 않는다는 사실을 그 파일의 주석에 명시하여,
나중에 누군가 "파이프라인이 왜 검사에서 빠졌지"라고 물을 때 답이 코드 안에 있게 한다.

## 5. `normalize` — 이 설계의 핵심

### 문제

국토부 데이터의 단지명은 흔들린다.

```
"래미안대치팰리스"  "래미안 대치팰리스"  "래미안대치팰리스1단지"
"e편한세상"  "이편한세상"  "E편한세상"
"우성"  "우성아파트"  "우성1차"
```

**두 방향으로 틀릴 수 있고 성격이 정반대다.**

| 오류 | 결과 |
|---|---|
| 과소병합 (안 합침) | 같은 단지가 목록에 여러 번. **지저분하지만 시세는 맞다** |
| 과대병합 (잘못 합침) | 다른 단지의 거래가 섞여 **엉뚱한 시세가 나온다. 조용하고 위험하다** |

### 채택: 보수적 키 + 이상 신호 리포트

키: `법정동코드 | 건축년도 | 최소정규화된이름`

최소 정규화는 **공백·특수문자 제거, 대소문자 통일**까지만이다.
**차수·단지·아파트 접미사는 건드리지 않는다** — "우성1차"와 "우성2차"는 실제로 다른 단지다.

기본값이 "안 합침"이므로 **틀리는 방향이 안전하다.**

### 대안과 그 기각 사유

| 접근 | 기각 사유 |
|---|---|
| 적극적 정규화 (접미사 제거 + 유사도 병합) | "우성1차"/"우성2차"가 조용히 합쳐진다 |
| 외부 단지 마스터(K-apt 등) 대조 | 데이터 소스가 하나 늘고, 그쪽 표기도 국토부와 안 맞는 문제가 그대로 생긴다. 문제를 옮길 뿐일 수 있다 |

### 출력 레코드

```ts
interface NormalizedTrade {
  complexKey: string;        // 법정동코드|건축년도|정규화명
  regionCode: string;        // 시군구 코드 5자리
  legalDongCode: string;
  complexName: string;       // 원본 표기 중 대표
  builtYear: number;
  exclusiveAreaSqm: number;
  floor: number;
  price: number;             // 원 단위 정수
  contractDate: string;      // YYYY-MM-DD
}
```

## 6. 이상 신호 리포트

정답지가 없으므로, **정답지 없이 계산 가능한 의심 신호**를 뽑는다.
이것이 다음 버전에서 정규화 규칙을 조일 유일한 근거다.

| 신호 | 판정 기준 |
|---|---|
| **과소병합 후보** | 같은 `법정동코드 + 건축년도`인 서로 다른 키 쌍 중, 정규화명의 **레벤슈타인 거리 ≤ 2** 또는 한쪽이 다른 쪽의 **접두사**인 경우 |
| **과대병합 의심** | 한 키·같은 평형·최근 6개월 거래 중 **최고가 ÷ 최저가 ≥ 2.0** 이고 거래 건수 ≥ 4인 그룹 |
| **평형 분할 의심** | 한 단지에서 **1㎡ 차이로 인접한** 두 평형 버킷이 **둘 다 거래 3건 미만**인 경우 |
| **저신뢰 비율** | 전체 평형 중 `lowConfidence` 비율 |
| **수집 실패** | 파싱 실패 건수, 건너뛴 시군구·월 (`fetch`가 남긴 로그에서 읽는다) |

**임계값은 코드가 아니라 설정 파일에 둔다**(`scripts/pipeline/report-config.json`). 리포트를 보고
조이는 것이 이 단계의 목적이므로, 조이는 행위 자체가 코드 수정이어서는 안 된다.

임계값의 근거는 다음과 같으며, 모두 **관찰 후 조정할 초기값**이다:

- 편집거리 2 — `"우성"` vs `"우성1차"`는 거리 2로 잡히고, `"우성1차"` vs `"우성2차"`도 거리 1로 잡힌다.
  후자는 실제로 다른 단지이므로 **리포트는 "합쳐라"가 아니라 "확인하라"는 뜻이다.** 자동 병합하지 않는다
- 최고÷최저 2.0 — 같은 단지 같은 평형에서 6개월 내 2배 차이는 층·향으로 설명하기 어렵다
- 거래 4건 이상 — 2~3건은 우연히 벌어질 수 있어 신호로 쓰기에 약하다

사람이 읽는 마크다운으로 낸다.

## 7. 단계별 계약

### `fetch`

- 입력: 시군구 코드 목록(설정 파일) × 최근 12개월
- **증분 캐시**: `raw/{코드}-{년월}.json`이 있고 **지난 달 이전이면 건너뛴다.**
  이번 달은 거래가 계속 쌓이므로 항상 다시 받는다
- 순차 호출 + 지연. 429/5xx에 지수 백오프
- **부분 실패 시 이전 스냅샷을 유지한다.** 깨진 데이터를 내려보내느니 하루 묵은 것이 낫다
- **수집 로그를 `data/fetch-log.json`에 남긴다.** 시도한 시군구·월, 캐시로 건너뛴 것, 실패한 것과
  그 사유. `report`가 이 파일을 읽어 "수집 실패" 항목을 만든다 — 그러지 않으면 `report`는
  `normalized.json`만 보므로 **애초에 수집되지 않은 데이터의 부재를 알 방법이 없다**

### `aggregate`

단지키 × **전용면적을 1㎡ 단위로 반올림한 평형**별로:

- 최근 6개월 거래 **중위값** (짝수 개면 가운데 둘의 평균, 원 단위 내림)
- 거래 건수, 최고/최저
- 3개월·1년 변동률
- `lowConfidence: true` — 최근 6개월 거래가 **3건 미만**일 때. 제외하지 않고 표시한다

**반올림의 한계를 인정한다.** 84.4㎡와 84.6㎡는 실제로 같은 평형인데 84와 85로 갈린다.
조용히 뭉개는 대신 **리포트의 "평형 분할 의심"이 잡는다.**

### `emit`

`data/`에 세 파일: `complexes.json`, `regions.json`, `manifest.json`.

**평범한 JSON으로 낸다.** 화면 3~5번이 이를 번들에 넣을지(`import`) 런타임에 받을지는
그때 결정하면 되고, 두 방식 다 같은 파일을 읽는다. `emit`이 알 필요가 없다.

`manifest.json`에 데이터 버전, 생성 일시, **실거래 데이터 기준일**, 적용 룰셋 버전을 담는다.

## 8. 아직 확인하지 못한 것

**국토부 실거래가 API의 응답 형식.** 최근 공공데이터포털 API는 `_type=json`을 지원하는 경우가
많지만 이 API가 그런지 확인하지 못했다.

따라서 **`fetch` 구현의 첫 단계는 한 건을 실제로 호출해 응답 형식을 확인하는 것**이다.
XML이면 파서 의존성이 하나 늘어난다. 지어내지 않고 확인 후 진행한다.

## 9. 검증 방식

지역코드 목록을 **설정 파일**로 뺀다. 처음에는 서울 몇 개 구만 넣고 돌린 뒤,
이상 신호 리포트를 사람이 확인한다. 그 다음 목록만 넓혀 수도권 전체로 간다.
**코드는 바뀌지 않고 설정만 바뀐다.**

## 10. 에러 처리

| 상황 | 처리 |
|---|---|
| API 키 없음 | 즉시 실패 + 발급 방법 안내 |
| API 일시 실패 | 백오프 재시도 → 그래도 실패하면 해당 월만 건너뛰고 리포트에 기록 |
| 응답 스키마 변경 | 파싱 실패를 조용히 넘기지 않고 실패 건수를 리포트에 남김 |
| 거래 0건인 시군구·월 | 정상. 빈 파일로 캐시해 재호출 방지 |
| 이전 스냅샷 존재 | 새 수집이 실패해도 덮어쓰지 않음 |

## 11. 테스트 전략

- **`normalize`·`aggregate`가 테스트의 대부분이다.** 순수 함수라 픽스처만으로 전부 검증된다
- **중위값 경계**: 홀수 개, 짝수 개, 1건, 0건
- **정규화 키**: 공백/대소문자 변형이 같은 키로 묶이고, **차수가 다른 이름은 다른 키로 갈리는지**
- **리포트 신호**: 일부러 과소병합·과대병합·평형 분할을 심은 픽스처에서 각각 잡히는지
- **`fetch`**: HTTP를 모킹해 재시도·백오프·증분 캐시 건너뛰기만 검증. 실제 네트워크는 테스트하지 않는다
- `data/`는 gitignore 대상이므로 테스트는 픽스처를 별도 디렉토리에 둔다
