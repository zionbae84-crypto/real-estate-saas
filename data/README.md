# data/ 산출물 스키마

이 파일은 `emit`이 파이프라인을 돌릴 때마다 다시 쓴다. 필드 이름만 보고
화면에서 잘못 렌더링하기 쉬운 것들(특히 창 크기·단위·null 의미)을 정의한다.

## complexes.json (EmittedComplexUnit[])

정렬 순서: complexKey 오름차순, 같으면 areaBucket 오름차순 — 파일은 gzip
전이라도 항상 같은 순서로 나온다(같은 입력 → 같은 바이트). complexKey가
문자열이라 `"11680-1000"` < `"11680-99"`처럼 사람이 읽는 번호 순서와는
다르지만, 순서 자체가 결정론적이면 되는 자리라 문제되지 않는다.

| 필드 | 타입 | 단위/창 | null 의미 |
|---|---|---|---|
| complexKey | string | **국토부가 주는 단지 고유 ID(`aptSeq`)** 그 자체. `"11680-314"` = 시군구코드-일련번호. 파이프로 이어붙인 합성 키가 아니다 — 옛 형식(`지역\|법정동\|건축년도\|정규화명`)은 이름 표기가 흔들리면 한 단지가 갈리고 같은 이름의 다른 단지는 뭉쳤다 | 없음(항상 존재) |
| complexName | string | 화면에 쓸 단지 이름. 그 단지의 거래 중 **가장 많이 쓰인 표기**(같으면 더 최근 계약, 그래도 같으면 사전순)를 고른 것이라 입력 순서와 무관하게 늘 같다. **키가 아니다** — 묶는 것은 `complexKey`가, 보여 주는 것은 이 값이 한다 | 없음 |
| regionCode | string | 시군구 코드 5자리 | 없음 |
| legalDongName | string | 법정동명 | 없음 |
| builtYear | number | 건축년도(연도) | 없음 |
| areaBucket | number | 전용면적을 1㎡ 단위로 반올림한 값(**표시용**). 84.4·84.6이 84·85로 갈릴 수 있다(report.md의 "평형 분할 의심" 참고) | 없음 |
| maxExclusiveAreaSqm | number | 이 버킷(complexKey × areaBucket)에 실제로 들어간 거래들의 **최대** 전용면적(원본 실수값, 반올림 안 함). **85㎡ 임계값(농특세·정책대출 자격) 판정은 areaBucket이 아니라 이 값으로 해야 한다** — areaBucket은 반올림이라 85.4㎡가 85로 내려와 초과분을 놓칠 수 있다. 평균·중위값이 아니라 최대값인 이유: 면적이 클수록 부담이 커지는 쪽이 이 제품이 택해야 하는 보수적 방향이라서다 | 없음 |
| tradeCount | number | 최근 6개월 거래 건수 | 없음 |
| minPrice / maxPrice | number | 원 단위 정수. 최근 6개월 창 안의 최저·최고가 | 없음 |
| minFloor / maxFloor | number \| null | 위 가격 범위를 만든 **바로 그 거래들**(같은 최근 6개월 창) 중 층을 믿을 수 있는 거래의 최저층·최고층. **가격을 보정하라고 있는 값이 아니다** — 층별 가격 모델을 만들거나 "이 층이면 얼마쯤"을 계산하면 감정평가 영역이고, medianPrice를 산출물에서 뺀 것과 같은 이유로 하면 안 된다. 용도는 하나뿐이다: 사용자가 자기가 보는 매물의 층과 스스로 견주게 하는 것 | 믿을 수 있는 층이 그 창에 하나도 없었다는 뜻. **0층·1층으로 채우지 않는다** |
| unknownFloorCount | number | 그 창의 거래 중 층을 믿을 수 없었던 건수(1층 미만이거나 정수가 아닌 값 — 지하 표기 등). 모르는 층을 채우지 않는다 대신 몇 건이 그랬는지를 남긴다. 0이면 그 창의 모든 거래가 층 범위에 들어 있다 | 없음 |
| landLeasehold | `"Y"` | `"N"` | null | **토지임대부 여부.** 토지 소유권이 없는 집이라 사는 사람이 반드시 알아야 하는 "사지 말아야 할" 신호다. 창은 최근 6개월이 아니라 그 단지의 **모든** 거래 — 시간과 무관한 성질이라서다. 한 건이라도 `"Y"`면 `"Y"`, `"Y"`가 없고 모르는 값이 섞였으면 `null`, 전부 `"N"`일 때만 `"N"`이다(놓치는 쪽이 낙관 방향이라 판정을 한쪽으로 기울였다). **화면 연결은 아직 안 했다** — 지금은 데이터에만 있다 | `null`은 **모른다**는 뜻이다. **"아니다"가 아니다** — `!== "Y"`를 "토지임대부 아님"으로 읽으면 안 된다 |
| lowConfidence | boolean | 대표가(내부적으로 계산하는 중위값) 신뢰도. 최근 6개월 거래 건수가 lowConfidenceMinTrades 미만이면 true | 없음 |

## 내보내지 않는 필드

파이프라인은 내부적으로 `medianPrice`(최근 6개월 중위값)와
`changeRate3m`·`changeRate12m`(및 그 부속 건수·저신뢰 필드)까지 계산하지만
(`scripts/pipeline/aggregate.ts`), 이 산출물(complexes.json)에는 **담지 않는다.**

- `medianPrice`: 특정 가격을 대표값으로 단정하면 감정평가에 저촉될 수
  있어, 화면은 가격을 항상 `minPrice`~`maxPrice` 범위로만 말한다.
- `changeRate3m`/`changeRate12m`류: 부모 스펙 §12가 금지하는 "수익률
  예측"으로 읽히기 쉽다.

둘 다 화면 표시가 금지된 값이라 애초에 쓸 곳이 없다 — 타입에서(그리고
이제 산출물에서도) 빼 두면 실수로 화면에 흘릴 방법 자체가 사라진다.

**주소(`roadNm`·`roadNmCd`·`bonbun`·`bubun`·`jibun`·`umdCd`)도 담지 않는다.**
다만 이유가 다르다 — 금지된 값이라서가 아니라 **아직 쓸 화면이 없어서**다.
주소는 거래 한 건의 성질이지 단지×평형의 성질이 아니라 집계 단계에서 이미
자리가 없고, 나중에 지오코딩을 붙일 때 필요한 것은 `data/raw/`의 거래별
주소이지 여기 실린 대표 주소 하나가 아니다. 담으면 번들만 커지고 정확도는
오히려 떨어진다. 원본은 `data/raw/`에 그대로 남아 있다(위 "data/raw/*.json"
참고).

## manifest.json (Manifest)

| complexCount | number | 등장한 서로 다른 complexKey 개수(단지 수) |

## monthly.json (MonthlySeries)

월별 시세 시계열이다. complexes.json과 **별도 파일**로 낸다 — 화면에
붙이는 것은 이 파이프라인 작업과 별개의 결정이라, 지금은 파이프라인이
만들기만 하고 **`src/`는 이 파일을 import하지 않는다**
(`scripts/pipeline/monthly.test.ts`의 가드가 지킨다).

최상위는 객체(`Record<string, MonthlyPoint[]>`)다 — 배열이 아니다.

- 키: `complexKey|areaBucket` (complexes.json 집계와 같은 키 형식이라
  같은 키로 조인할 수 있다). 키는 오름차순 정렬돼 있다.
- 값: 그 단지×평형의 월별 시계열, **월 오름차순** 배열. 각 원소:

| 필드 | 타입 | 의미 |
|---|---|---|
| month | string (YYYY-MM) | 계약월 |
| minPrice / maxPrice | number | 원 단위 정수. 그 달 거래들의 최저·최고가 |
| tradeCount | number | 그 달 거래 건수 |

complexes.json과 같은 규칙으로 **`medianPrice`도 변동률도 없다** — 화면이
낼 수 있는 것은 범위(min~max)와 건수뿐이라는 방침(위 "내보내지 않는
필드" 참고)이 월별 시계열에도 그대로 적용된다.

complexes.json과 달리 "최근 6개월 대표가" 하나로 뭉치지 않고, raw 거래가
커버하는 모든 달을 각각 담는다(asOf 이후 미래 거래만 제외).

## data/raw/*.json (수집 캐시 — 산출물이 아니다)

`fetch`가 시군구·월마다 하나씩 쓰는 원시 거래 캐시다. gitignore 대상이고
번들에 실리지 않는다 — `complexes.json`을 만드는 **입력**일 뿐이다.

봉투 형식: `{ schemaVersion, trades, failures, cancelled, truncated? }`

`schemaVersion`은 거래 한 건의 필드 구성이 바뀔 때마다 올린다. 값이 지금
코드와 다르면 `fetch`는 캐시 없음으로 보고 다시 받고(로그에
`cacheSchemaMismatch`), `run`은 **읽지 않고 멈춘다.** 조용히 읽으면 새 필드가
없는 옛 거래들이 단지 키 `undefined` 하나로 뭉쳐, 서로 아무 상관 없는
거래들이 한 단지인 척하는 산출물이 "정상" 얼굴로 나간다.

거래 한 건(`trades[]`)의 필드:

| 필드 | 타입 | 의미 | null/없음 의미 |
|---|---|---|---|
| regionCode | string | 시군구 코드 5자리 | 없으면 그 거래는 파싱 실패 |
| aptSeq | string | **국토부가 주는 단지 고유 ID**(`"11680-314"` = 시군구코드-일련번호). 단지 키가 이 값이다 | 없거나 공백뿐이면 파싱 실패 — 어느 단지인지 모르는 거래는 넣을 곳이 없다 |
| legalDongName / complexName / builtYear / exclusiveAreaSqm / floor / price / contractDate | — | 기존 필드. 금액은 원 단위 정수 | 없으면 파싱 실패 |
| landLeasehold | `"Y"` | `"N"` | null | **토지임대부 여부.** 토지 소유권이 없는 집이라 사는 사람이 반드시 알아야 하는 신호다 | `null`은 **모른다**는 뜻이지 "아니다"가 아니다. 응답이 `"Y"`/`"N"` 외의 값(공백 한 칸, 필드 없음, 예상 못한 코드)을 주면 여기로 온다 |
| address | object | 도로명·지번 주소. **지금은 저장만 하고 화면에 쓰지 않는다** — 나중에 지오코딩(입지분석)을 붙일 때의 전제다 | 각 하위 필드가 개별적으로 null일 수 있다 |

`address`의 하위 필드(`roadNm`·`roadNmCd`·`bonbun`·`bubun`·`jibun`·`umdCd`)는
전부 `string | null`이다. 숫자로 와도 문자열로 보존한다 — `bonbun`은
`"0746"`(문자열)과 `1284`(숫자)가 섞여 오고, `bubun`의 `"0000"`은 숫자로
바꾸면 선행 0이 사라져 다른 값이 된다. 공백 한 칸(`" "`)과 빈 문자열은
`null`로 접는다 — `""`는 "주소가 빈 문자열"이라는 없는 사실이고 `null`은
"모른다"는 사실이라, 나중에 지오코딩이 이 둘을 구분해야 한다.

주소가 없다고 그 거래를 버리지는 않는다. 주소는 **가격·부담 계산에 전혀
쓰이지 않으므로** 없다고 그 거래의 시세 근거가 나빠지지 않는다.

**`landLeasehold`와 주소는 `complexes.json`에 담기지 않는다** — 아래 "내보내지
않는 필드" 참고.

## location.json (입지 입력 + 지도 참고 표시)

두 화면이 같은 파일을 나눠 쓴다 — `scripts/pipeline/location.ts`가 굽고
`src/data/location.ts`가 정적으로 들여온다.

- **입지 화면**(`src/components/LocationFacts.tsx`, `src/lib/location/`)은
  `elementarySchools`·`subwayStations`만 쓴다. 반경 안 개수를 세고
  "학구도가 아니다"라는 고지와 함께 낸다.
- **지도**(`src/components/ComplexMap.tsx`)는 `middleSchools`·`highSchools`도
  함께 쓴다. 지하철역 마커와 같은 성격의 참고 표시일 뿐 — 반경 집계도,
  배정학교 판정도 하지 않는다.

**이 둘을 섞지 않는다.** `middleSchools`·`highSchools`는 `src/lib/location/`
(입지 화면 엔진)에 절대 들여오지 않는다 — 아래 `elementarySchools[]` 절이
설명하는 "학교급을 늘리면 학군처럼 읽히기 시작한다"는 원칙이 그 경계
안에서만 지켜지면 되고, 지도의 순수 위치 표시는 그 판단을 하지 않는다.

**거래 파이프라인(`npm run pipeline`)과 별개로 돈다** — 입력이 `data/raw/`의
실거래 캐시가 아니라 `data/sources/`의 표준데이터라서다. 다시 만들려면:

```
npm run pipeline:location
```

### 최상위 모양

```
{
  "schemaVersion": 3,
  "complexes":         [ { complexKey, lat, lon }, ... ],
  "subwayStations":    [ { id, name, lineName, lat, lon }, ... ],
  "elementarySchools": [ { id, name, lat, lon,
                           foundationType, foundedOn, address,
                           officeOfEducation, districtOfficeOfEducation }, ... ],
  "middleSchools":     [ { id, name, lat, lon }, ... ],
  "highSchools":       [ { id, name, lat, lon }, ... ]
}
```

**버전 3에서 초등학교에만 기본정보를 더했다**(설립·주소·교육청 — 아래
`elementarySchools[]` 절 참고). 2까지는 세 학교급이 전부 같은 네 필드였다.

다섯 배열은 각각 `complexKey` / `id` 오름차순으로 정렬한다 — 같은 입력이면
같은 바이트가 나와야 한다(`complexes.json`과 같은 규칙).

### complexes[] — 단지 좌표 (**지금은 빈 배열이다**)

| 필드 | 타입 | 의미 |
|---|---|---|
| complexKey | string | `complexes.json`의 `complexKey`와 같은 값(국토부 단지 고유 ID `aptSeq`). 이걸로 조인한다 |
| lat / lon | number | WGS84 위경도(도 단위). 소수점 이하를 자르지 않는다 — 소수 넷째 자리가 약 11m다 |

**아직 비어 있다.** 지번 주소를 지오코딩하려면 별도 API 키가 필요한데 아직
없다. 그래서 화면은 지금도 모든 단지에서 "아직 위치를 몰라요"를 내고,
그것이 정직한 상태다.

**좌표를 못 얻은 단지는 항목 자체를 넣지 않는다.** `lat: null`도, `0`도
아니다. 없는 키를 조회하면 자연히 "모른다"로 가지만, `null`을 값으로 두면
그 자리가 "확인해 봤는데 없더라"처럼 읽히기 시작한다.

**대체 좌표를 만들지 않는다.** 특히 두 가지를 하면 안 된다:

- 근처 단지의 좌표로 채우기
- 법정동 중심점으로 채우기 — 법정동은 한 변이 몇 km라, 그걸로 재면
  "역까지 300m"와 "역까지 2.5km"가 뒤바뀐다

둘 다 화면을 재는 데 성공시키고 숫자만 통째로 틀리게 만든다. 그 실패는
눈에 띄지 않으므로 이 제품이 가장 피해야 하는 종류다. 지오코딩이 실패한
단지는 **빠뜨리는 것이 정답**이다.

지오코딩 입력은 `data/raw/`의 거래별 `address`(지번: `umdCd`·`bonbun`·
`bubun`)다. **주소 자체는 이 파일에 담지 않는다** — 화면에 주소를 내지
않기 때문에 번들에 실을 이유가 없다.

### subwayStations[] — 지하철역 좌표

| 필드 | 타입 | 의미 |
|---|---|---|
| id | string | `노선번호-역번호`. 원본의 역번호는 운영기관마다 따로 매겨져 있어 전국에서 유일하지 않다(광주 101번과 대전 101번이 각각 있다). 그래도 겹치는 몇 행에는 `#2` 꼬리표가 붙는다. **화면에 나가지 않는 키일 뿐이다** |
| name | string | 역 이름 |
| lineName | string | 노선 이름 |
| lat / lon | number | WGS84 위경도 |

**환승역은 노선마다 항목이 따로 있다 — 역 단위로 합치지 않는다.** 원본이
노선별로 다른 행을 주고 그 행들은 좌표가 서로 다르다(노선별 승강장·출입구가
실제로 떨어져 있어, 상봉역의 두 행은 약 165m 차이다). 합치려면 좌표와 노선
이름 중 하나를 골라야 하는데 그건 우리가 모르는 것을 정하는 일이고, 나머지
노선의 거리를 통째로 틀리게 만든다. 엔진은 이 중복을 전제하고 가장 가까운
하나만 고르며, 룰셋 문구가 "여러 노선이 지나는 역이면 그중 한 노선만 적혀
있을 수 있어요"라고 말한다.

모든 필드가 똑같은 완전 중복 행(원본에 실제로 있다)만 뺀다 — 같은 사실을
두 번 싣는 것이라 빼도 잃는 사실이 없다.

좌표가 없거나 0인 행은 **넣지 않는다.** 엔진이 국내 범위 밖 좌표를 한 번
더 거르지만(`src/lib/location/assess.ts`의 `KOREA_BOUNDS`), 걸러진 뒤 남는
것이 하나도 없으면 그 줄은 "아직 못 실었다"가 된다 — 빈 목록을 "주변에
역이 없다"로 쓰지 않는다.

### elementarySchools[] — 초등학교 좌표 + 기본정보

| 필드 | 타입 | 의미 |
|---|---|---|
| id | string | 원본의 학교ID |
| name | string | 학교 이름 |
| lat / lon | number | WGS84 위경도 |
| foundationType | string | 설립형태 — 공립·국립·사립 중 하나 |
| foundedOn | string | 설립일자(YYYY-MM-DD) |
| address | string | 소재지 주소. **도로명주소를 쓰고 비어 있으면 지번주소로 물러난다** — 원본에서 초등학교 6,303곳 중 10곳이 도로명주소가 비어 있다 |
| officeOfEducation | string | 시도교육청명(예: 서울특별시교육청) |
| districtOfficeOfEducation | string | 교육지원청명(예: 서울특별시동부교육지원청) |
| phone | string? | 전화번호. **공시에 없으면 키가 없다**(285곳 중 50곳) |
| foundationForm | string? | 설립유형 — 단설·병설·부설·부속 |
| students | {total, male, female}? | 학생 수. `total`은 언제나 `male + female` |
| teachers | {total, male, female}? | 교원 수. 공시 "직위별 교원 현황"의 총계(기간제·강사 포함, 원어민강사 제외, 휴직은 남·여 안에 포함) |

**아래 넷은 다른 원본에서 온다** — 위 다섯이 위치표준데이터라면, 이 넷은
학교알리미 공시(`data/sources/school-info.csv`)다. 공시는 해마다 한 번이라
**오늘 기준이 아니고**, 그래서 파일 최상위에 `elementarySchoolInfoYear`가
함께 실리고 화면도 그 연도를 밝힌다.

**모르는 값은 키를 만들지 않는다** — `null`도 `0`도 아니다. `0`을 넣으면
"교원이 0명"이라는 틀린 사실이 되고, 없는 키는 화면에서 자연히 "그 줄을
내지 않는다"가 된다(`complexes[]`의 좌표와 같은 규칙).

**기본정보(아래 다섯 필드)는 초등학교에만 있다** — 사용자 지시로 지도에서
초등학교 마커를 누르면 띄우게 되며 실었다(`ComplexMap.tsx`). 중·고등학교에는
붙이지 않는다: 학교급을 늘려 기본정보까지 붙이면 화면이 "학군"처럼 읽히기
시작하고, 그건 이 앱이 하지 않기로 한 가치판단이다.

**전부 원본이 준 값 그대로다** — 우리가 만들거나 추정한 값이 하나도 없다.
`address`의 도로명→지번 대체만 우리가 고른 규칙이고, 둘 다 비면 빈
문자열로 두어 화면이 그 줄을 통째로 내지 않게 한다(없는 것을 아는 척하지
않는다). 전화번호·학생 수·교원 수는 이 원본에 아예 없다 — 넣으려면 다른
출처(학교알리미)가 필요하고, 아직 넣지 않았다.

**교육지원청명을 실은 이유**는 고지 문구와 짝이 맞기 때문이다. 배정은
학구도로 정해지니 "관할 교육지원청에 확인하라"고 말해 왔는데
(`rules/location-2026-08.json`의 `schoolZoneNote`), 정작 그 교육지원청이
어디인지는 말해 주지 못했다.

**초등학교만 담는다.** 중·고등학교는 넣지 않는다 — **입지 화면이** 말하는
것은 초등학교 하나뿐이고, 학교급을 늘리면 그 화면이 "학군"처럼 읽히기
시작한다. `운영상태`가 "운영"인 학교만 담는다(다닐 수 없는 학교를 세면
반경 안 개수가 실제보다 많아진다). 분교는 뺄 이유가 없어 그대로 담는다 —
다닐 수 있는 학교다.

### middleSchools[] / highSchools[] — 중·고등학교 좌표 (지도 참고 표시 전용)

| 필드 | 타입 | 의미 |
|---|---|---|
| id | string | 원본의 학교ID |
| name | string | 학교 이름 |
| lat / lon | number | WGS84 위경도 |

거르는 규칙은 위 `elementarySchools[]`와 완전히 같다(학교급만 다르다) —
`운영상태`가 "운영"인 학교만, 같은 상자(`targetBounds` +
`elementarySchoolBufferMeters`)만.

**소비하는 화면이 다르다.** 이 둘은 `ComplexMap.tsx`의 지도 위 참고 표시
(지하철역 마커와 같은 성격)로만 쓰인다 — 위 `elementarySchools[]`처럼 반경
안 개수를 세거나 "학구도가 아니다"를 판정하지 않는다. `src/lib/location/`
(입지 화면 엔진)은 이 두 배열을 들여오지 않는다 — 들여오는 순간 위
"초등학교만 담는" 원칙이 뚫린다.

### 이 파일에 담지 않는 것

- **단지 주소.** 지오코딩 입력으로만 쓰고 화면에 내지 않는다. (초등학교
  주소는 버전 3부터 담는다 — 사용자 지시로 지도에서 학교 기본정보를
  띄우게 되면서 "화면에 낸다"가 바뀌었다. 단지 주소는 그대로 담지 않는다.)
- **점수·등급·순위.** 이 제품은 입지를 평가하지 않는다. "학군 90점"·
  "교통 우수"는 가치판단을 사실처럼 포장한 것이고 검증할 수 없다 —
  `medianPrice`를 산출물에서 뺀 것과 같은 이유다. 산출 타입에도 그런
  필드가 없고(`src/lib/location/types.ts`), 여러 테스트가 어떤 입력에서도
  등급이 나오지 않는지 확인한다.
- **도보 시간·도보 경로.** 우리는 경로를 모른다. 화면이 내는 것은
  직선거리뿐이고, 그것이 걷는 거리와 다르다는 사실을 고지가 함께 말한다.

### 원본은 어디에 있나 — data/sources/

저장소에는 **컬럼만 슬림하게 추려** 원본 데이터를 보관한다.
추적 대상이고, `src/`가 들여오지 않으므로 번들에 실리지 않는다.
`data/raw/`(실거래 캐시)와 섞지 않는다 — 그쪽은 gitignore 대상이고 재수집이
덮어쓴다.
각 원본은 서로 다른 산출물을 만든다: `schools.csv`와 `subway-stations.csv`는
`data/location.json`을 만들고, `legal-dong-codes.csv`는 `data/legal-dong-codes.json`을
만든다.

| 파일 | 원본 데이터셋 | 데이터 기준일자 | 남긴 컬럼 |
|---|---|---|---|
| `data/sources/schools.csv` | 한국교육시설안전원 「전국초중등학교위치표준데이터」 (`한국교육시설안전원_초중등학교위치_20260320.csv`, 12,011행) | 2026-03-20 | 학교ID, 학교명, 학교급구분, 설립일자, 설립형태, 운영상태, 소재지지번주소, 소재지도로명주소, 시도교육청명, 교육지원청명, 위도, 경도 |
| `data/sources/subway-stations.csv` | 「전국도시철도역사정보표준데이터」 (`전체_도시철도역사정보_20260630.xlsx`, 시트 `표준데이터 역사`, 1,099행) | 2026-06-18 | 역번호, 역사명, 노선번호, 노선명, 역위도, 역경도 |
| `data/sources/legal-dong-codes.csv` | 국토교통부 「전국 법정동」(공공데이터포털, `data.go.kr/data/15063424`, 20,561행) | 2026-07-29 | 법정동코드, 시도명, 시군구명, 읍면동명 |
| `data/sources/school-info.csv` | 학교알리미 OpenAPI 공시(학교기본정보·성별 학생수·직위별 교원 현황, 285행) | 2025년 공시 | 학교ID, 학교명, 전화번호, 설립유형, 학생수(계·남·여), 교원수(계·남·여), 공시연도 |

`school-info.csv`만 **API로 받는다**(나머지 셋은 사람이 파일을 내려받는다).
`npm run pipeline:school-info`가 만들고, `.env`의 `SCHOOLINFO_API_KEY`가
필요하다 — 그 키는 이 단계에서만 쓰이고 브라우저 번들에는 들어가지 않는다
(`VITE_` 접두사가 없다). 자세한 것은 `scripts/pipeline/school-info.ts` 머리
주석에 있다.

**학교코드가 서로 다르다**: 우리 목록은 한국교육시설안전원 계열(`B000001839`),
학교알리미는 자기 코드(`S010000737`)를 쓰고 공식 대응표가 없다. 그래서
**같은 시군구 안에서 학교명이 정확히 같고 두 원본의 좌표가 300m 안일 때만**
한 학교로 잇는다. 285곳 전부 이어졌다.

세 파일 모두 UTF-8(BOM 없음)·LF이고, 행 순서를 정렬해 뒀다 — 학교는
학교ID 오름차순, 역은 노선번호·역번호·역사명·노선명 오름차순, 법정동은
법정동코드 오름차순이다(다시 받아 추려도 같은 바이트가 나오게 하려는 것이다).

학교 원본은 3.6MB인데 우리가 쓰는 컬럼은 열둘이라 2.9MB로 줄었다.
**주소 두 컬럼(지번·도로명)을 남긴다** — 버전 3부터 초등학교 기본정보를
화면에 내기 때문이다. 둘 다 남기는 이유는 도로명이 빈 학교(초등 6,303곳 중
10곳)에서 지번으로 물러나기 위해서다. 이 원본을 다시 받는 곳은
[학구도안내서비스 공공데이터](https://schoolzone.emac.kr/publicData/publicDataList.do)
(「초중고 학교 위치」)이고, 같은 데이터가 공공데이터포털
[15021148](https://www.data.go.kr/data/15021148/standard.do)에도 있다.
전화번호·학생 수·교원 수는 이 원본에 없다 — 다른 출처(학교알리미)가 필요하다.
**학교급을 미리 거르지 않고 12,011행을 그대로 둔 이유**는 "초등학교만
실렸다"를 원본과 맞대어 검사할 수 있게 하려는 것이다
(`scripts/location-data.test.ts`).

역 원본은 xlsx다. **xlsx 파서를 의존성에 넣지 않는다** — 파이프라인은 외부
파서 없이 돈다. 한 번 CSV로 바꿔 위 파일로 보관했고, 다시 만들 때 쓴 변환은
이것이다(python3 + openpyxl):

```
python3 -c "
import openpyxl, csv
wb = openpyxl.load_workbook('전체_도시철도역사정보_20260630.xlsx', read_only=True, data_only=True)
ws = wb['표준데이터 역사']
rows = list(ws.iter_rows(values_only=True))
head = list(rows[0]); idx = {h: n for n, h in enumerate(head)}
keep = ['역번호','역사명','노선번호','노선명','역위도','역경도']
out = [[str(r[idx[c]]).strip() if r[idx[c]] is not None else '' for c in keep] for r in rows[1:]]
out.sort(key=lambda r: (r[2], r[0], r[1], r[3]))
w = csv.writer(open('data/sources/subway-stations.csv','w',newline=''), lineterminator='\n')
w.writerow(keep); w.writerows(out)
"
```

### 어디까지 싣는가 — scripts/pipeline/location-config.json

전국 초등학교 6,303곳과 전국 역 1,099행을 통째로 싣지 않는다. 우리 단지는
서울 세 구(`scripts/pipeline/regions.json`의 11650·11680·11710)뿐이다.
다만 **거르는 기준을 코드에 박지 않는다** — 지역을 넓히는 날 설정만 고쳐
다시 구울 수 있어야 한다.

설정이 정하는 것은 셋이다:

| 키 | 값 | 뜻 |
|---|---|---|
| targetBounds | lat 37.43~37.56 / lon 126.96~127.18 | 우리 단지가 있을 수 있는 범위. 세 구의 행정경계를 넉넉히 감싼다 |
| subwayBufferMeters | 4000 | 그 상자 밖으로 이만큼까지의 역도 싣는다 |
| elementarySchoolBufferMeters | 1500 | 그 상자 밖으로 이만큼까지의 초등학교도 싣는다 |

**버퍼가 이 설정의 핵심이다.** 단지가 있는 구만 담으면 구 경계 바로 밖의
역·학교가 사라지고, 화면은 더 먼 역을 "가장 가까운 역"이라고 조용히 말한다
— 아무 데도 드러나지 않는 종류의 오류다.

- 역: 엔진이 반경 없이 **가장 가까운 하나**를 고르므로, 상자 안 어느
  점에서든 전국에서 가장 가까운 역이 실려 있어야 한다. 전국 원본으로 상자를
  격자로 훑어 잰 "가장 가까운 역까지의 거리"의 최대값이 약 3,584m라 그보다
  여유 있는 4,000m로 뒀다.
- 초등학교: `rules/location-2026-08.json`의 `radiusMeters`(1,000m) 안만
  세므로 그보다 크기만 하면 빠뜨리지 않는다. 멀리 있는 학교는 애초에 세지
  않아 번들만 커지므로 1,500m로 뒀다.

`scripts/location-data.test.ts`가 이 두 부등식을 원본으로 직접 다시 확인한다
— 상자를 넓히면 먼저 그 검사가 깨진다.

그 결과 실린 것은 **지하철역 306행(고유 역사명 기준으로는 그보다 적다) /
초등학교 285곳 / 단지 좌표 0개**이고, `data/location.json`은 144KB다
(기본정보를 더한 뒤의 값이다).

## school-zones.json (초등학교 통학구역 도면)

사용자 지시로 지도에서 초등학교를 누르면 **통학구역(학구도) 경계**를 함께
그린다. 이 파일이 그 경계다.

### 무엇이 아닌가

**배정 결과가 아니다.** 통학구역은 교육청이 정한 "이 구역에 살면 이 학교로
갈 수 있다"는 경계일 뿐이고, 실제 배정은 공동통학구역·근거리 배정·학교
사정으로 달라진다. 원본도 "수시"로 갱신된다. 그래서 화면은 이 경계를
그리면서도 룰셋의 `schoolZoneNote`("배정은 거리순이 아니라 학구도로 정해지니
교육지원청에 확인하라")를 **항상 함께** 낸다 — 경계가 생겼다고 그 고지를
빼지 않는다.

### 모양

```
{
  "schemaVersion": 1,
  "dataAsOf": "2026-03-20",
  "zones":    { "<학구ID>": { name, shared, rings: [[lon0, lat0, dlon1, dlat1, ...], ...] } },
  "bySchool": { "<학교ID>": ["<학구ID>", ...] }
}
```

| 필드 | 의미 |
|---|---|
| zones[].name | 학구명(예: `서울학동초통학구역`) |
| zones[].shared | 공동통학구역인가(원본 `HAKGUDO_GB`가 `1`). **참이면 그 구역 안에서 학교를 고를 수 있다** |
| zones[].rings | 경계 링. **접혀 있다** — `[경도0, 위도0, 다음점과의 차이, ...]`를 1e-6도(≈11cm) 단위 정수로 적는다. 좌표쌍을 그대로 적으면 470KB인데 접으면 216KB고, 정밀도는 그대로다 |
| bySchool | 학교ID → 학구ID들. **키가 없으면 그 학교는 통학구역이 없다**(사립·국립) |

푸는 쪽은 `src/data/school-zones.ts`다.

### 한 학교에 구역이 여럿일 수 있다

우리 지역 272곳 중 85곳이 그렇다(공동통학구역이 섞이거나 구역이 떨어져
있다). 그래서 `bySchool`의 값이 배열이고, 화면도 링 하나당 폴리곤 하나로
그린다.

### 통학구역이 없는 학교가 있다

우리 지역 초등학교 285곳 중 **13곳은 통학구역이 아예 없다.** 확인해 보니
전부 사립 12곳·국립 1곳이었다 — 추첨·선발로 뽑으므로 배정 구역이라는 것이
성립하지 않는다. 화면은 그때 빈칸을 두지 않고 "이 학교는 통학구역이
없어요"라고 말한다. `src/data/school-zones.test.ts`가 "공립인데 구역이 없다"
또는 "사립인데 구역이 있다"가 생기면 깨진다.

### 원본과 다시 만드는 법

| 항목 | 값 |
|---|---|
| 원본 | 한국교육시설안전원 「초등학교 통학구역 및 공동통학구역」(SHP) + 「학교-학구도 연계정보」(CSV) |
| 받는 곳 | [학구도안내서비스 공공데이터](https://schoolzone.emac.kr/publicData/publicDataList.do) (공공데이터포털 [15021149](https://www.data.go.kr/data/15021149/standard.do)·[15021158](https://www.data.go.kr/data/15021158/standard.do)에도 있다) |
| 기준일자 | 2026-03-20 |
| 좌표계 | 원본 EPSG:5186(중부원점, 미터) → 저장 시 WGS84 |

**원본 SHP는 저장소에 넣지 않는다 — 55MB다.** `data/sources/`의 다른 원본들과
다른 점이라 여기 적어 둔다. 대신 굽는 스크립트를 저장소에 둔다:
`scripts/pipeline/school-zones.py`(받는 법·돌리는 법이 그 파일 머리에 있다).

**파이썬인 이유**는 `subway-stations.csv`를 xlsx에서 바꿀 때와 같다 — 검증된
도구로 한 번 변환하고, 파이프라인 본체는 그 도구에 의존하지 않는다. 여기서는
SHP 파서와 좌표계 변환이 필요한데, 특히 좌표계 변환을 손으로 짜면 화면은
멀쩡히 그려지고 경계만 몇 미터씩 어긋나는 — 눈에 안 띄는 — 실패가 난다.

**그래서 굽는 단계와 테스트가 같은 교차검증을 한다**: 학교 좌표(전혀 다른
원본인 위치표준데이터에서 온 값)가 자기 통학구역 안에 드는가. 272곳 전부
들어야 하고, 하나라도 벗어나면 좌표계 변환을 의심해야 한다
(`src/data/school-zones.test.ts`).

경계는 1e-5도(≈1.1m) 허용오차로 단순화한다(60,389점 → 21,288점). **더 굵게
잡지 않는다** — 통학구역 경계는 "길 어느 쪽에 사는가"를 가르는 선이라 몇
미터를 흐리면 실제로 갈리는 집이 생긴다.

## 참고

- 이상 신호(한 단지 ID에 이름 여러 개, 화면에서 구분 안 되는 동명 단지,
  가격 범위가 지나치게 넓은 평형, 평형 분할 의심, 수집 실패/파싱 실패/거래
  0건/데이터 잘림/캐시 손상·형식 불일치, 해제 거래)는 여기 담기지 않는다 —
  `data/report.md`를 본다. 그 리포트는 사람이 읽고 이 데이터를 내보낼지
  판단하는 절차의 일부다.
- 임계값(lowConfidenceMinTrades 등)은 `scripts/pipeline/report-config.json`에
  있다.
